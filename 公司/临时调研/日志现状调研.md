# 日志现状调研

> 调研目的：为"日志用纯文本还是数据库"短会提供事实依据。只读查证，未改代码。

---

## 一、日志落点（4 处）

| # | 落点 | 位置 | 格式 | 说明 |
|---|------|------|------|------|
| 1 | **工单日志** | `工单/{列}/*.日志.md` | Markdown 纯文本 `[时间戳] 文本` | **主日志**。每个工单伴生一个 `.日志.md`，由引擎工具.写日志() 追加 |
| 2 | **后端控制台** | `运行状态/as_log/backend.*.log` | 无结构 stderr/stdout（Python 警告、traceback） | 启动脚本 `tee` 捕获，已 gitignore |
| 3 | **会话事件** | `运行状态/会话事件/{sid}.jsonl` | JSONL（每行一条 JSON） | 事件总线持久化，供断线重连 replay |
| 4 | **协同会议** | `协同/会议/{mid}.json` + `{mid}.md` | JSON 结构体 + 渲染 Markdown 纪要 | 会议事件记录、开工/交办/回执 |

辅助记忆文件（不算日志但也是运行时写入）：`岗位/*/记忆.md`、`记忆库/{人名}.md`、`项目记忆/*.md`、`信箱/*.md`。

## 二、格式

- **纯文本 Markdown**：工单日志，格式为 `[MM-DD HH:MM:SS] 自由文本`，无字段化结构
- **JSONL**：会话事件，每行一条 `{"类型": "发言", "发言人": ..., "内容": ..., "t": "HH:MM:SS"}`
- **JSON**：会议数据（含事件数组）、控制文件（`.控制.json`）
- **无结构**：后端 as_log，Python 运行时警告和 print 输出直接落盘

**未使用 Python `logging` 模块**。全项目零 import logging。

## 四、现有模块依赖关系

```
引擎工具.py  ← 定义 日志() / 写日志() / 原子写()
  ├── 看板数据.py  ← 读 .日志.md，用正则解析产物状态（"写入文件："/"完成："）
  ├── 协同.py      ← import 日志 from 引擎工具，读日志文本做协同摘要
  ├── _历史_勿执行/引擎.py  ← 大量 写日志() 调用（~25处，历史代码）
  └── 活_本人.py   ← 通过 progress 回调把过程事件透出给前端

事件总线.py  ← 独立模块，JSONL 持久化
办公室.py    ← print() 做少量控制台输出
```

## 五、改数据库会牵涉的文件与风险

### 必改文件（5 个）

| 文件 | 改动点 | 工作量 |
|------|--------|--------|
| `引擎工具.py` | `写日志()` 改为 DB INSERT；`日志()` 路径逻辑需保留或适配 | 小 |
| `看板数据.py` | `_产物状态()` / `_日志过程()` 目前用正则扫日志文本提取文件名和阶段——要么改成从 DB 字段查，要么日志写入时同步结构化 | **大** |
| `协同.py` | 读 `.日志.md` 做协同摘要的逻辑要改 | 中 |
| `事件总线.py` | `_追加持久()` 从 JSONL 改 DB；`_载入持久()` 从文件改 SELECT | 中 |
| `办公室.py` | 前端取日志的接口（如有）需适配 DB 查询 | 小 |

### 核心风险

1. **正则解析耦合**：`看板数据.py` 用正则 `写入|追加)文件：`、`完成：` 扫日志原文提取产物和状态。改 DB 后要么日志内容保持同格式文本（那 DB 的意义打折），要么在写入时拆成结构化字段（写入量大改）。
2. **前端直读文件**：前端大概率直接读 `.日志.md` 展示工单进度（文件路径约定好了的）。改 DB 后需要新增 API 接口，前端也要改。
3. **无现成 DB 依赖**：项目目前零数据库依赖（纯文件系统），引入 DB 意味着新增 sqlite3/sqlalchemy 等依赖、建表、迁移脚本。
4. **并发写入**：当前 `原子写()` 用 `tmp + rename` 做原子性，多线程场景已验证。改 DB 要注意 SQLite 写锁 / 并发性能。

### 不动也行的理由（纯文本优势）

- 工单日志是人类可读的 Markdown，船主/测试工程师可以直接打开文件看
- 正则解析虽然丑但跑通了，工单量不大（单机），性能无瓶颈
- `.日志.md` 伴随工单文件移动（`移动伴随文件()`），文件系统天然保持一致性

---

## 六、结论（供短会用）

**现状**：项目日志 = 纯文本 Markdown 文件为主，JSONL 事件流为辅，零数据库依赖，零 logging 模块使用。

**如果改 DB**：核心难点不在写入（改一个函数），而在下游 `看板数据.py` 的正则解析链路和前端直读文件的约定要同步改。牵涉 5 个文件 + 前端。

**建议讨论方向**：
- 如果只想要"可查询/可统计" → 可以在保留 `.日志.md` 的同时，写入时多写一条结构化记录到 SQLite（双写），渐进迁移
- 如果只是觉得日志不规范 → 统一 `写日志()` 的格式（加 JSON 头或固定字段），不改存储层，改动最小
- 全面切 DB → 可行但当前体量未必值得，需评估前端改动成本
