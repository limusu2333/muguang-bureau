# 岗位技能 · 需求澄清与拆解
> 目的：让项目经理把船主一句自然语言判断清楚：能直接处理就直接处理，需要别人时才变成可并行、可验收、可追溯的派活/验收项，而不是把模糊需求直接丢给员工。

## 拆解前先判定
1. 目标：船主要的是界面体验、真实流程、模型核验、文档同步、还是产品行为。
2. 证据：哪些结论必须看文件，哪些必须跑命令，哪些必须真实 API 核验。
3. 影响：会不会改变历史项目室、生成文件、消耗模型额度、触碰密钥或改变项目资料。
4. 停线：做到哪一步必须回到船主或舟那里拍板。

## 派活成形规则
- 每件活只交给一个岗位，且只写一个边界内的文件/目录集合。
- 验收命令要证明目标，不只证明“文件存在”。
- 涉及真实模型、视觉、权限、外部资料时，必须把核验动作写进派活说明。
- 需求不完整时先派“探查/核验”，不要伪装成实现活。
- 每件活必须写预算依据、预计字数、预计token。token是模型处理文本的计量单位，会影响额度和成本。
- 预算步数要覆盖完整闭环：读资料/核验、实现或写入、读回自检、完成复盘、必要测试交接。简单文档任务也通常不能低于4-5步。

## 输出格式
`目标复述 / 拆解表 / 覆盖核对 / 风险与请示点 / 等船主确认项`
