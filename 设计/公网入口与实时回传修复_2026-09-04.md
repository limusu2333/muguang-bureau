# 公网入口与实时回传修复

> 日期：2026-09-04
> 开发区：`30_开发公司` / `agentscope-migration`
> 状态说明：本文主体记录 v1.21 发布前的故障与第一次失败尝试。候选 `candidate-20260904T122509Z-8bfec085` 及部署 `deployment-20260904T123223Z-36a35b39` 已失败并完整回退，不得重试；修复后来由新候选成功发布进 `暮光v1.21beta版`。当前事实见文末“后续发布结果”。

## 现场事实

公网登录已经能通过固定 SunnyNgrok 地址进入正式用户公司。测试用户在大厅发送“你们好”后，页面一直显示“公司正在回应”；同一时间健康区显示 `FileNotFoundError`。

只读核对得到两条独立事实：

1. 用户公司在 `2026-09-04 10:32:05` 接单，`10:32:10` 已完成；任务记录、会话事件和大厅记录均已保存回答“陈志康，你好！老钟在。”。模型和公司执行链没有卡住。
2. 健康接口在 Linux 用户容器里调用了 macOS 服务管理命令 `launchctl`，容器内没有这个命令，因此整个健康快照抛出 `FileNotFoundError`。

## 根因

### 健康检查

自动备份定时任务属于 Mac 宿主能力。旧代码没有区分运行系统，导致正式用户的 Linux 容器也检查 `LaunchAgent`，并直接执行 `launchctl`。

### 回答卡在“正在回应”

回答过程使用 SSE（服务器持续向网页推送事件的长连接）。旧后端同时使用“没有正文长度”和 `Connection: keep-alive`，任务结束后没有给反向代理一个明确的正文结束边界。经过公网代理时，事件可能被继续等待或缓存。

前端又在任务期间暂停普通大厅刷新，只信这条实时连接；如果连接处于“没有新数据、也没有明确报错”的半断状态，页面就会无限显示“正在回应”。本机直连路径短，因此不容易暴露。

本机入口还没有把一端断开传给另一端，现场日志中积累了大量 `Task was destroyed but it is pending`，说明已断开的转发任务没有正常收尾，会继续占用连接资源。

## 开发版修复

1. 自动备份检查先识别运行系统：Mac 宿主继续核对真实 `LaunchAgent`；Linux 用户容器不再调用 `launchctl`，也不把“容器没有 Mac 定时任务”报成异常。
2. SSE 响应明确使用 `Connection: close`，并发送禁止代理缓存的响应头；一轮任务结束后，代理能够确认响应已经结束。
3. 新增 `/run-events` 只读接口。网页在保留 SSE 实时显示的同时，每秒按事件序号补收遗漏事件。两条通道收到的是同一份已持久化事件，前端按序号去重，不会重复发言或改变顺序。
4. 实时连接中断时不再立刻判整轮失败；短请求继续补收。两条通道连续 30 秒都无响应时才明确结束等待并提示失败，页面不会永久卡住。
5. 本机 TCP 转发在任一端断开时向另一端传递结束信号，使连接任务正常退出。

这不是拿最终大厅记录替代实时体验。实时通道正常时仍按原速度展示思考、动作和发言；公网漏掉事件时才由普通短请求补上同一条事件流。

## 验证结果

- Python 编译检查通过。
- 新增 Linux 容器健康回归：确认不会调用 `launchctl`，也不会生成错误的 Mac 定时任务告警。
- 新增事件补收回归：确认按序号只返回缺失事件，运行态和终态来自真实任务记录。
- 新增前端契约回归：确认 SSE 保留、补收按序号去重、连续失联会明确结束。
- 新增转发断开回归：确认连接结束信号会传给另一端。
- `make check`：公司隔离回归 `157/157`，多用户单元测试 `276/276`。

## 首次发布尝试与紧急修复

首次发布尝试 `deployment-20260904T123223Z-36a35b39` 被交付物校验挡住，页面提示“当前正式后台没有完整运行”。现场核对发现，正式版三个端口当时实际由临时兜底进程 `com.xj.multiuser.formal-fallback` 统一承载；同时还残留一个指向已移除目录 `30_开发公司_多用户施工` 的旧 `com.xj.multiuser.supervisor` 启动项。两套旧运行方式并存，使发布器无法把正式宿主识别为完整的 `control/admin/rerank` 三角色，因此正确地拒绝继续发布。账号容器、共享平台和活动版本锁始终保持 v1.2，没有发生半发布。

使用正式恢复入口时又发现，宿主准备函数错误地无参数调用“登记开发源”。开发源登记必须由开发管理安装流程显式传入，恢复现役正式宿主不应猜测或改写开发源。本次已删除这次错误调用，并新增回归测试，固定“准备或恢复宿主不得改开发源登记”。

恢复后已核对：三个正式宿主分别由 `com.xj.multiuser.control`、`com.xj.multiuser.admin`、`com.xj.multiuser.rerank` 独立运行，状态和源码身份均为 v1.2；指向废止目录的旧启动项已删除；两个在用账号容器、共享平台、活动版本锁和公网入口均未改变。完整 `make check` 通过：公司隔离回归 `157/157`、多用户单元测试 `277/277`，前端生产构建和脚本检查通过。

旧候选 `candidate-20260904T122509Z-8bfec085` 已固定在修复前提交，不能继续确认或直接重试。下一次发布必须从包含本次紧急修复的新提交重新生成候选。
