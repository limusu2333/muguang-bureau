## 0. 先把 bug 说准（这不是我们的错觉，有学名）

串味有正式学名 **Task Interference / 任务切换串味**（arXiv 2402.18216）——对话历史当成 in-context 示例，用户切新话题时把模型拽回旧任务。5数据集15种切换实测，很多切换造成显著性能下降。另一篇（arXiv 2505.06120）叫它 **continuation bias / 过早承诺**：模型一旦锁定一个方向就顽固沿旧假设走。

**所以"不处理、纯靠模型自觉"不是选项。** 但四路调研高度一致的另一句更关键——**这四家（mem0 / Letta / Character.AI / 学术）没有一家靠"给最新一句加当前锚"，全都靠"结构分层 + 位置(recency) + 轻量判定"。船主否掉手搓加锚，方向完全正确，且有源码/文献背书。**

## 1. 我们现在的底盘长什么样（先照镜子）

看 `构造聊天消息`（活_本人.py:378-404）和 `_聊天系统提示`（:340-371），我们**已经做对了一半**：

| 项 | 现状 | 判定 |
|---|---|---|
| 真多轮数组纯净 | `records[-30:]` 只放原始对话，检索记忆没塞进数组 | ✅ 已对 |
| 检索/背景分层 | 记忆精华 + 近期公司摘要放在 **system 里**，和对话数组物理分开 | ✅ 已对 |
| 说话人前缀 | 「实例主人：」/「同事名：」写进 content，自己回复不带前缀 | ✅ 已对（且是根因修复过的） |
| 最新句在末端吃 recency | 数组最后一条=最新大厅消息 | ✅ 天然成立 |
| **话题延续判定** | **无** | ❌ 缺——串味主因 |
| **末位引导 turn** | **无**（只有插话续写时才临时塞，那是别的场景） | ❌ 缺 |
| 固定灌30句 vs 按需收缩 | **一刀切固定30句** | ⚠️ 旧话题永远在窗口里抢戏 |

**结论：我们不缺分层，缺的是"让模型显式判断‘接旧 vs 起新’、并据此决定带多厚上下文"的那一层。** 这正好是船主要的"既治串味、又保 follow-up 手感"。

## 2. 收敛出的成熟做法（3 个，带出处）

### 做法 A ·【首选】Character.AI 的 Prompt Poet「末位引导 turn」
**出处**：blog.character.ai/introducing-prompt-poet ; arXiv 2402.18216（Task Interference）。

prompt 不是一整段，而是有序块：`system → 历史(带 author 前缀) → 当前 query → 末位一条极短"回应引导" turn`。这条引导 turn 靠 recency 拿到最高权重——**这才是业界版"加权最新"，不是往用户原话里塞锚。**

引导 turn 写成**柔性**的：新招呼/新话题就当新开场、别复述旧话题；只有明显指代上文（"那个/刚才/继续"）才接续。判定权交给模型，短 follow-up 靠指代词自然接上，"你在吗"靠"当新开场"这句放行。

**为什么适合我们**：和我们真多轮数组零冲突，只在数组末尾**追加一条 turn**，不动历史、不改用户原话——正好绕开船主否掉的"给最新句加锚"。

### 做法 B ·【搭配 A】AstrBot 心流(Heartflow) 的「对话连贯性 continuity 维度」
**出处**：github.com/advent259141/Astrbot_plugin_Heartflow（main.py 判定 prompt）。

Heartflow 判定里第5维专评 continuity（0-10）：**是上次回复的延续→高分；完全无关→给中等分(5)而不是0分；无上次回复→默认5。** 关键设计：**无关时给中分、不压制**——这天然不伤 follow-up。

我们**不需要养小模型**（那是群聊压插嘴频率用的，1v1/必回场景照搬会把该接的短 follow-up 压到阈值下→变生硬，坑）。1v1 只取它的判定思想：让主模型**一次 structured output 顺带吐一个 continuity 判断**，据此决定带厚/带薄上下文。

### 做法 C ·【治本·检索侧】mem0 的「relevance 阈值 + recency 重排 + 只在切话题时收缩历史」
**出处**：mem0.ai/blog/context-engineering-in-multi-turn-ai-agents ; arXiv 2510.10276（lost-in-the-middle） ; getmaxim 上下文管理。

- 检索出的旧话题设**相关度门槛**，不达标不注入；命中也按 recency 重排、旧话题沉底。**治本在检索侧，别指望 prompt 层兜底。**
- 30句别一刀切全灌：**近端 6~10 轮逐字**（保 follow-up 手感，`verbatim beats extracted`，arXiv 2601.00821 明确警告近端别摘要），**更早的 20 多句改成按当前句语义检索只召回相关 3~5 条**——旧话题不相关就根本不进上下文。

## 3. 落到我们底盘的具体设计（改哪、怎么组）

**总原则：分三步，从最轻改到治本，可以只上第一步先看效果。**

### 第一步（必做，最小改动，治大头）：加末位引导 turn — 改 `构造聊天消息`

在 `构造聊天消息`（活_本人.py:404 `return msgs` 之前）追加一条**柔性引导 turn**，role=user、放在整个数组最末：

```
【最新一句以实例主人刚说的为准。请先判断它是"新招呼/新话题"还是"接续上文"：
- 若是简短招呼（如"你在吗""在""忙不忙"）或明显新话题：自然地当新开场回应它，不要主动把上面聊过的旧事翻出来续；
- 只有当他明显在指代上文（"那个/刚才/继续说/接着"）时，才接续上一个话题。】
```

**为什么这样写**（每条都有踩坑背书）：
- 不写"只回应最新句、忽略上文"——那会 over-anchoring，该接的 follow-up 接不住（文献：模型会 drift/ignore 已建立语境）。
- 留口子"明显指代才接续"——把裁量权给模型，别一刀切（Heartflow 无关给中分的思想）。
- 放在**末尾**吃 recency，不塞进用户那句——绕开船主否掉的硬锚。

### 第二步（推荐，治 follow-up 手感）：让模型显式带 continuity 判断

有两种落法，选一：
- **轻量版**：把上面引导 turn 的判定语气用足即可，不改代码结构。够治"你在吗"这类。
- **结构版**：`聊天唤醒`（:415）让主模型 structured output 顺带吐 `{is_new_topic, is_short_followup}`；`is_new_topic=true` 时把近端窗口临时缩到最近 1~2 轮再让它正式作答，`is_short_followup=true` 时什么都不动。**解析失败兜底默认"当新话题、带薄上下文"**（比默认续聊安全——Heartflow 源码专门写了 JSON 解析兜底+重试）。

### 第三步（治本，可后置）：`构造聊天消息` 的 `records[-30:]` 拆成"近端逐字 + 远端检索"

- 近端：`records[-10:]` 逐字进数组（现在的逻辑）。
- 远端：第11~30句**不再逐字灌**，改成拿最新句去 `search_hall_history`/FTS 召回**相关的 3~5 条**，压成一条带**`【往期背景·仅供参考，以最新句为准】`** 标签的消息，放在近端窗口**之前**（primacy 位，不夹中段——lost-in-the-middle）。
- 检索加 relevance 阈值，不达标远端就空着。

> 注：第三步动了检索链路，改动面最大。**建议先上第一、二步观察，第三步作为下一轮。**

### system 提示要不要动？
`_聊天系统提示`（:340）**基本不用动**，记忆精华/近期摘要留在 system 是对的（已分层）。唯一可选：把判定那句从 system 挪进**末位引导 turn**（第一步已含），别在 system 里常驻——文献踩坑：常驻硬指令会让模型倾向把每句都当新话题切割，伤连续。**判定按需在末位放一份，别常驻。**

## 4. 对比我手搓的"硬加当前锚"——差在哪、为什么成熟做法手感更好

| | 我手搓的硬加锚 | 成熟做法（末位引导 turn + 柔性判定） |
|---|---|---|
| 作用位置 | 塞进**最新那句用户消息里** | 独立的**末位 turn**，不碰用户原话 |
| 机制 | 给当前句一个**硬指向** | 靠**结构位置(recency)+柔性判定**，让模型自己认 |
| 短 follow-up（"那个再核下"） | 被锚强行掰断，该接的接不住 | 指代词触发自然接续，手感不变 |
| 新招呼（"你在吗"） | 也被锚指向旧话题 → 串味没根治 | 引导语明说"当新开场"，放行 |
| 文献/源码背书 | 无——四家框架**没有一家**这么干 | Character.AI 生产范式 + Heartflow 源码 + mem0/Letta |

**一句话**：硬加锚是"我替模型钉死它在回哪"，钉死就一刀切，该接的旧话题和该起的新话题只能二选一。成熟做法是"给模型一个末位的、柔性的提醒 + 干净的结构信号，让它自己认"——所以它能同时接住短 follow-up 和认出新招呼。这正是 Heartflow "无关给中分而非0分"、Prompt Poet "引导而非命令" 的共同智慧。

## 5. 给船主的明确推荐

**首选：先上第一步（末位柔性引导 turn），观察真实对话；手感确认后再上第二步（continuity 判定）。第三步（检索侧收缩30句）留作下一轮治本。**

**理由**：
1. 第一步改动极小（只在 `构造聊天消息` 末尾加一条 turn），风险最低，且直接对准"你在吗被答成旧话题"这个现象。
2. 它是 Character.AI 生产环境验证过的范式，**不碰用户原话、不碰历史数组**，天然满足船主"别手搓加锚、别伤 follow-up"两条红线。
3. 我们的分层已经做对了一半（检索在 system、数组纯净、带前缀），缺的就是这最后一块拼图，性价比最高。

**不建议现在做的**：养小判定模型（1v1 必回场景多余开销 + 意愿闸门会压掉该接的 follow-up）；MemGPT 那套 OS 式自管理内存（太重，我们已有四区文件+摘要+FTS）；固定砍N条改成 cache-aware 截断（我们单机小规模用不上）。

## 6. 需要船主拍板 / 亲验的点

1. **末位引导 turn 的措辞你亲眼过一遍**——尤其"简短招呼当新开场"这句会不会太硬、把某些其实想续的短句也切了。这是唯一可能伤手感的地方，得你用真实对话验。
2. **先只上第一步、还是一二步一起上？** 我的建议是先第一步单独看效果（能隔离出到底是"引导 turn"生效还是别的）。
3. **第三步要不要做、什么时候做**——它动检索链路（把30句拆成近端逐字+远端召回），是治本但改动面大。可以等第一步观察完再定。
4. **continuity 走"轻量版(只靠引导语)"还是"结构版(structured output)"**——结构版更可控但要改 `聊天唤醒` 的输出解析、加兜底重试。
5. **验收怎么算过**：建议拿"你在吗 / 在忙吗 / 吃了吗"三句贴在一段旧话题后面跑，看会不会再被答成旧话题续写；再拿"那个再核下 / 继续说"验短 follow-up 还接不接得住。两组都过才算治好。
