# 本地告警表达与动态决策施工记录（2026-08-13）

## 为什么改

原问题卡的视觉和交互已经成立，但内容仍把 `RuntimeError`、`ValueError`、供应商状态和内部流水直接交给船主；三个按钮又固定为“同意 / 稍后 / 补充”，没有回答“同意什么”。这会让告警停在“通知出错”，而不是帮助船主作出下一步决定。

本轮目标是两件事：

1. 把机器故障翻译成普通人能看懂的事实说明。
2. 根据问题类型给出具体动作，例如“重新备份并核验”“恢复这项任务”“核对模型权益”。

## 最终边界

采用“规则系统决定，微型本地模型翻译”的组合，而不是让模型接管告警：

- `工具/健康.py` 根据任务状态、错误类别和系统区域生成标题、建议、动作编号、按钮标题与按钮说明。
- `工具/告警表达.py` 只把原始技术原因翻译为一到三句人话；它不能修改标题、建议和按钮，也不能执行动作。
- `工具/机房.py` 保存刚刚发给前端的告警原件。用户提交时只接受服务器登记过的告警指纹和系统白名单中的动作，不相信浏览器回传的整张告警。
- 模型不可用、超时或输出不合格时，原规则卡立即可用，不阻断健康检查和处理链。
- 健康告警处理任务本身从新告警源中排除，避免一次处理失败再次制造同类问题卡。

这条边界来自真实试跑：若让 4B 模型同时改写建议和按钮，它偶尔会补入原始证据没有的限制。收紧后，模型只翻译技术原因，决定权永久留在确定性系统和船主手里。

## 本地模型

- 模型：`mlx-community/Qwen3.5-4B-4bit`
- 固定版本：`0e7ffd5c629ef7719d4cbc04069232580bfa9d9c`
- 运行方式：Apple `mlx-lm` Python API 直连，但只允许先生 Mac 的宿主精排服务加载；主开发办公室与正式用户通过宿主端口/内部中继请求，不在各自进程或 Linux 容器复制模型。
- 默认目录：`~/Library/Application Support/沐光破事部/models/Qwen3.5-4B-4bit`
- 权重文件：`model.safetensors`，约 2.83 GiB。
- 安装入口：先安装 `requirements.txt`，再运行 `make local-alert-model`。

宿主服务按需加载模型并把告警送入有界表达队列。第一次即时请求最多短等 1.8 秒；未完成时先给规则版，生成结果缓存到宿主进程内，后续健康轮询换成人话版。主开发办公室和正式用户都走这一个宿主实例；桥接失败时不在调用方启动本地模型。

## 前端

- 问题卡直接读取每条告警自己的动作，不再硬编码三个固定决定。
- “补充”仍保留自由文本；“稍后”不派发任务；其他具体动作按原文交给项目经理。
- 窄屏问题卡不再自动粘到底部遮住标题；有问题卡时关闭对话区顶部渐隐，并把卡片开头滚入视野。
- 自动对齐只在问题卡刚出现时发生；45 秒健康轮询不会把正在向下阅读的用户拉回顶部。
- 进度按当前未处理告警的真实位置显示，不再永远写 `1 / 总数`。
- 2026-08-29 收口提醒与决策的边界：右上角 `×` 只收起本次提醒，不偷偷提交“稍后”；每张卡可选“不再提示”，只忽略当前问题指纹，问题内容变化后仍会再提醒。前端不再对后端已经提供的告警重复合成第二张卡，避免“处理过又弹出”和“告警已刷新”假冲突；本轮随 `dca6e38` 提交。

- 模型下载完整性检查通过，权重约 2.83 GiB。
- 独立进程实测：模型加载 3.87 秒；第一张故障翻译 0.91 秒。
- 宿主服务与内部中继的离线契约测试通过；正式用户容器未安装 MLX，`/alert-render` 失败时首卡来源保持“规则”。真实发布/切换前不启动公网或加载现役封存版本模型。
- 同一张实测卡的标题、建议和动作逐字保持规则原值，只有技术详情被替换；`RuntimeError`、`ValueError` 包装不再显示。

- Playwright 实看桌面与 `390×844` 窄屏；窄屏最初发现标题被星环层遮住，修复后复截图通过。

## 当前边界

- 模型缓存只在办公室进程内，重启后会重新加载和预编译当前告警。
- 这不是自动修复系统。点击具体动作后，仍由项目经理核对原记录并按公司权限制度处理；费用、密钥、删除文件或扩大权限仍须另行请示。
- 规则版是正式兜底，不是残缺模式。即使模型目录被删、模型加载失败或本地推理超时，用户仍能看到具体问题并作决定。
