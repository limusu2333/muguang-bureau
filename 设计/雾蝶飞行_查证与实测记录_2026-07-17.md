## 一、需求书里有两条与实况不符，已实测纠正

### 1. 轴向说反了（这是"横着飞"的真正病根）

需求书第五节写：「场景局部 `+X` 是腹部到头部的前向，`+Y` 是背部向上，`+Z` 是左右翼展方向」。

**实测（three.js 加载模型、烧动画、读世界坐标，非截图推断）**：

| 量 | 实测值 | 结论 |
|---|---|---|
| 腹部→头部 | 归一化 `(0.0065, 0.1403, 0.9901)` | **+Z 是前向** |
| 右翼尖→左翼尖 | 归一化 `(0.9994, -0.0324, 0.0075)` | **+X 是翼展** |
| 翼尖行程最大轴 | X=0.060 / **Y=0.107** / Z=0.033 | +Y 是背部向上（这条需求书是对的） |

即 **X 和 Z 说反了**。旧代码 `MistButterflyField.tsx:522` 的注释白纸黑字照抄了这个错误说法，然后 `makeBasis(flightForward, flightUp, flightRight)` 把**翼展轴对准了飞行方向**——蝴蝶是真的在横着飞。

**前面多轮调运动参数全部无效，是因为病根不在参数里，在姿态映射装反了。**

### 2. 根节点的 -90°X 旋转是被抵消的

需求书说根节点 `Sketchfab_model` 自带 -90°X 旋转（属实），但它下面的 `GLTF_SceneRootNode` 有 +90°X，**两者抵消，净旋转为零**。凭这条去推轴向会二次犯错。

## 二、模型实况（全部实测）

- 片段 `OrganicWingCycle`，时长 `9.5833s`，471 条轨道，157 根骨头 —— 与需求书一致。
- 片段**不是匀速循环**，而是「静止 → 一段爆发拍翼 → 复位」：0–2.0s 高举微动，2.1–7.6s 真拍翼（周期 0.24–0.36s），7.6s 后落回展平。
- **无缝循环窗口**：`t ∈ [2.6055, 2.9948]`，周期 `0.3893s`，首尾姿态失配 `0.00027`（0 为完美）。代码即用这一段循环。
- 拍幅 157°（顶 +80°、底 -45°），与论文 Table 3 的 0–150° 同量级。
- 叶素来自**真实蒙皮网格**：30 个站位，按顶点主导骨骼分组，面积由三角形实算，法线用 PCA 拟合翅膀平面（顶点法线在闭合薄壳上会自相抵消，模长只剩 0.21，不可用）。

### 这个动画缺了论文三个自由度里的两个（实测，非假设）

| 自由度 | 实况 | 后果 |
|---|---|---|
| 拍翼 flapping | 有 | — |
| **扭转 feathering** | **没有**：下拍/上拍的面积加权"拍板程度"比 = **0.944 ≈ 1.0** | 下拍挣的升力被上拍原样还回去，**任何正确的准定常模型下净升力都是零**；视觉上就是船主骂的"**像合页**" |
| **扫掠 sweep** | **没有** | 翅膀只会朝下拍水、从不向后推气 → **推力在所有频率、所有拍翼平面倾角下全为负**（纯阻力）。能悬停颠簸，但永远走不动 |

两者都已按论文的参数化补上。补扫掠后实测：**推力由负转正（−0.099 → +0.292 W），升力同时翻倍（0.259 → 0.589 W）**。

## 三、论文这条线的查证结论

- **没有任何官方代码可复用**。Qiang Chen 主页只挂 PDF 和视频；NSF 记录明确注明代码未公开；2024 年那篇同样无代码。
- GitHub 上 `Li-Jia-Jun/WebGPU-Butterfly` 虽引用该论文，但**没有实现它的物理**：grep 全部源码，`lift|drag|aerodynam|vortex` **零命中**，拍翼就是一句 `sin(time*speed)`，气动是它 README 里的"未来改进"。
- 顺带纠正需求书一处：2022 那篇**不是 SIGGRAPH 论文**，是 TOG 41(3) 常规期刊卷（SIGGRAPH 2022 是 41(4)）。
- **所以本实现是按论文的运动关系自己写的，绝不冒充用了原代码。**

### 论文印出来的升力系数不能用

`Cl(α) = -0.0095953α² + 0.090635α - 0.34182`，代入角度制后**全域为负**（α=0° 时 -0.34，α=90° 时 **-69.9**），物理上不可能是升力系数。已弃用，改用薄板准定常标准式：

- `Cl = 1.8·sin(2α)` —— 峰值 1.8 是 Dickinson et al. 1999 (Science 284:1954) 在动态缩放昆虫翼上实测、含前缘涡的量级
- `Cd = 0.028 + 1.9·sin²α`

## 四、这一程修掉的自身 bug（都是实测撞出来的，不是推理）

1. **蒙皮世界坐标算错**：SkinnedMesh 不能用 `mesh.matrixWorld`，必须走骨骼矩阵（three.js `applyBoneTransform` 那条路）。
2. **翼展在错误时刻量**：在拍翼顶点量翼展，翅膀正收拢，量出 0.0358 而非真实 0.0766 → 面积错 20 倍。已改为全周期取最大。
3. **扭转轴符号反了 → 左右翼升力精确抵消**：两片翅膀的骨骼局部 X 轴本就朝各自翼尖向外，**同角度即天然镜像对称**；我多加的左右反号把它变成了**滚转指令**，滑翔升力因此恒等于 `0.00`。（扫掠用的是共同的机体 Y 轴，那里的反号是对的。）
4. **⭐ `poseWings` 不幂等（毒化了整条标定链）**：我假设 `mixer.update(0)` 会把骨骼四元数重置回动画值，然后在上面**乘**扭转——**它不重置，于是每调用一次就累乘一次**。滑翔姿态搜索调了几千次，评出的"最优"（升阻比 5.05）最终根本重建不出来（重建为 −1.88）。改为**从动画曲线直接采样该相位的四元数并赋值**，与 mixer 用同一套插值 → 搜索值与重建值现已分毫不差。
   - **这条正是《查证5问》第 3 条的现场复发：我从没验过那个假设，黑盒猜了。**
5. **滑翔姿态选错判据**：原按"升力最大"选，选出的是高迎角**降落伞姿态**（升阻比 1.04 = 下滑 45°，那是坠落）。改按**最大升阻比**选（滑翔机姿态）→ **5.14（下滑 11°）**。
6. **`Cd₀` 定死了滑翔天花板**：最佳升阻比 ≈ `1.8/(2√(Cd₀×1.9))`。原 `Cd₀=0.1` → 天花板 4.0，搜索果然顶在 3.3。薄光滑膜翼侧向迎流只有摩擦阻力，`0.028` 才是诚实值。（Cd₀ 对**拍翼**升力几乎无影响，所以一直没被发现——**滑翔才是生死攸关的那个**。）

## 五、被实测否掉的思路（记下来免得后人重走）

- **倾斜拍翼平面当油门**：即使倾到 45°，推力仍是 −0.12（始终为负），只赔升力不给推进。**推力必须靠扫掠。** 已从代码删除。
- **降低 `Cd₀` 能救拍翼升力**：0.40→0.03 实测升力 0.448→0.440，**纹丝不动**。假设错误，幸好先测后改。
- **靠拍翼频率控高度**：无扭转时升力对频率几乎不敏感（2Hz 与 12Hz 都是 0.15W）。补扭转+扫掠后才恢复正常。
- **机头对准航点**：航点在高处 → 机头仰到 0.95 → **升力跟着倒向水平 → 爬不上去 → 永远够不着 → 仰头原地打转**。航向必须只取水平分量，靠翅膀爬升。
- **用运动学直接扳转机头**：速度靠物理跟不上 → 侧滑 → 转弯半径过大。改为**压坡度让升力产生向心力、机头跟着速度走**（这样"头朝飞行方向"是物理结果而非调出来的指标）。
- **翼载越低越优雅**：错。质量 0.016g 时可用速度窗口只有 0~0.5 m/s，一俯冲到 1.0+ 就 **升力崩塌（0.83→−2.17）→ 越快越掉 → 发散**。**没有质量就没有惯性，没有惯性就没有重量感**——正好是船主要的反面。配平速度提到 0.9 m/s 后质量 4 倍（0.063g），包线打开（1.2 m/s 仍有 3.13W 升力）。
- **俯仰完全跟随航迹角**：会掉进俯冲发散——沉 → 低头 → 竖直升力少 → 更沉。实测台架 3.7W 的一拍在实飞只兑现 1.0W，纯粹被姿态吃掉。需要高度时必须限制低头（改出俯冲）。

## 七、诚实交代：没达到的

1. **朝向误差不达标**（中位 21.4°，要求 <12°；95 分位 98.7°，要求 <35°）。原因已定位：这只生物每一拍都被踹一下，**瞬时速度矢量在一个拍周期内摆动几十度**，而需求书 §六.4 又同时要求"侧倾俯仰转向必须有限速和阻尼、不能突然抽动"——**两条指标在物理上互相拉扯**。按拍周期平均后误差降到 18°，仍未进 12°。这一条需要船主拍：是放宽指标，还是牺牲一部分颠簸感（那会掉重量感）。
2. **材质还是原模型的橙色帝王蝶贴图**，没做需求书 §七 的珍珠/薄膜/半透明/冷暖微虹彩。这一程全部预算花在飞行上了。
3. **翼尖滞后 / 翼根先受力**（§七）没做。
4. **点击减速、弹层、姓名岗位跟随**（§九）只做了跟随点验证，没做完整交互。
5. **窄窗口**没逐一验（只验了 1400×900）。
6. **没跑帧率实测**（需求书 §十要求接近 60fps）。
7. 慢动作时标 `TIME_SCALE=0.4` 是**明写的选择**：按 Froude 相似律等价于把生物放大约 6 倍。物理内部自洽，但它是为了"优雅"选的，不是物理必然。

# 追加：2026-07-17 晚 · 船主打断后的滑翔重做

船主原话：「**不用管颜色**」「**飞的太快了**」「**滑行的时候没有风的感觉，一滑行好像是在自由坠落不是滑行**」。
材质线当场停手（颜色他最后自己改）。以下只做滑翔和速度。

## 决定性诊断：滑翔物理本身完美，是控制器不让它发生

撇开控制器做纯滑翔积分（只给初速度 + 重力 + 滑翔姿态），**从 0.6 / 0.9 / 1.2 任意初速度出发，1~1.5 秒内全部收敛到同一个平衡**：

```
速度 0.89 m/s · 垂直速度 -0.170 · 垂直加速度 ay = 0.00 · 下滑角锁定 11.0°
4 秒滑行：水平掠过 3.49 米，只掉 0.68 米
```

而实飞的"滑翔"段平均 ay = **-1.76 ~ -2.27**（持续加速下坠）。**滑翔从来没发生过**，船主看到的是滑翔的头 0.2 秒瞬态被反复重播。

## 揪出的 bug 链（每一个都是实测撞出来的）

1. **滑翔姿态按"升力最大"选** → 选出高迎角**降落伞姿态**，升阻比 1.04（下滑 45°）=坠落。改按**最大升阻比**选 → **5.14（下滑 11°）**。
2. **`Cd₀=0.1` 定死滑翔天花板**（最佳升阻比 ≈ `1.8/(2√(Cd₀·1.9))` = 4.0，搜索果然顶在 3.3）。薄膜翼侧向迎流只有摩擦阻力 → `0.028`。**Cd₀ 对拍翼升力几乎无影响，所以一直没被发现——滑翔才生死攸关。**
3. **翼载太低 = 没有惯性 = 没有重量感**（正是船主要的反面）：质量 0.016g 时可用速度窗口只有 0~0.5 m/s，一俯冲到 1.0+ 就升力崩塌（0.83→−2.17）发散。配平速度 0.45→0.9 → 质量 4 倍（0.063g），包线打开（1.2 m/s 仍有 3.13W）。
4. **舞台配不上生物**：一次自然滑翔要掠 3.5 米，舞台只有 1.5 米（15 翼展），转弯半径 3.6 厘米，速度全耗在急转上。`PPM 900→480` → 舞台 2.9 米（30 翼展）。
5. **天花板高 1 厘米** → 高度门槛 **0 / 3015 帧** 命中，全靠"拍满 40 下"退出，而拍数只在整拍累加、整拍恰是**速度波谷** → 永远在最慢的一瞬被踢进滑翔。**我为此白改了两轮速度门槛**（0.88→0.7→0.72），因为那个条件根本轮不到判断。
6. **"高且快"物理上互斥**：爬升就是拿速度换高度，最高点必然最慢。
7. **⭐ 俯仰符号反了（总凶手）**：`applyAxisAngle(left, pitch)` 里正 pitch 是**低头**，而下滑时 `pathAngle` 是**负**的。我写 `pitch → pathAngle`，于是下滑 10° 时机头被**抬起** 10°，**迎角 = 航迹角的两倍**（实测航迹 10° → 迎角 18°，吻合）。航迹越陡迎角越大 → 阻力暴涨 → 速度崩 → mush → 翻跟头（迎角一路 4°→29°→92°→153°）。
8. **拍翼和滑翔要的机头姿态相反**（改对符号后立刻暴露）：滑翔时机头必须**严格贴航迹**（否则迎角失控），拍翼时必须**基本水平**（否则升力倒掉、爬不动，实测机头仰 46° 时爬升直接死）。一套规则套两种状态是之前顾此失彼的根源。

## 教训

- **我改 PPM 时没同步复核依赖它的量**（天花板按半高比例算），造成差 1 厘米的死锁，然后对着错的旋钮白调两轮。**改一个尺度参数，要把依赖它的量全部重算一遍。**
- **连续两次改动数字一模一样 = 强信号**：不是物理，是那条路径根本没被执行。当时该立刻去查条件命中率，而不是继续调参。
- **纯物理隔离测试是这一程最值钱的一步**：它把"滑翔物理"和"控制器"彻底分开，证明前者完美，后面所有的力气才没白花在错的地方。

## 2026-08-03 · 启动幕与主题过渡闭环

船主截图确认，旧实现会在主题重建途中露出一帧半成品：背景已经变了，两侧栏和人员文字却还停在中间状态。现改成“先遮住、再换世界、等首帧、最后揭开”，而不是拿固定延时猜模型何时加载完。

- **应用启动前**：`index.html` 自带极轻的静态启动幕；React、WebGL 和雾蝶模型还没执行时就已有稳定画面，不先闪白屏。启动幕读取上次主题，只决定深/浅底色，不加载重资源。
- **接管启动**：React 挂载后先用同构的运行时幕接住静态幕；深空等粒子画布完成第一帧，雾中等模型加载且至少一个个体完成第一帧，才进入揭幕。
- **主题切换**：320ms 窄光缝遮满旧主题后才卸载；新主题没有发出 `ready` 前不会露出。准备完成后用 640ms 反向揭开。7 秒只是一道故障兜底，防资源异常时永久盖住界面，不是正常切换计时器。
- **资源边界**：旧主题仍同步清理画布、动画帧和贴图；遮罩只是把重建过程藏好，不让两套主题并跑。
- **减少动态效果**：系统开启“减少动态效果”时，遮/揭缩到 30/90ms，启动线停止循环。
- **双击启动**：`打开办公室.command` 不再固定睡 1.2 秒后撞端口，而是每 0.1 秒检查首页；首页真实返回后才打开浏览器，最长等 12 秒并给出明确错误。

取法依据：MDN 的 View Transition 生命周期强调“捕获旧状态、更新 DOM、等新状态可用后过渡”；Apple HIG 要求运动有目的、短而精确，加载时应尽快给反馈并避免让等待显得失控。现役实现没有直接引入 View Transition API，因为两套主题含 WebGL 模型和显式资源卸载，使用自己的准备信号更可控。

- MDN: https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API/Using
- Apple Motion: https://developer.apple.com/design/human-interface-guidelines/motion
- Apple Loading: https://developer.apple.com/design/human-interface-guidelines/loading
