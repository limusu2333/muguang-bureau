## 一、先把 bug 的根说清（不是"时间设短了"，是"计时器语义错位"）

我们现在这一行（`工具/活_本人.py` 第 763 行，`唤醒本人`；聊天版在第 492 行 `聊天唤醒`）：

```python
ev = await asyncio.wait_for(_流.__anext__(), timeout=模型流超时秒)  # 300s
```

`wait_for(__anext__())` 度量的是**"两个流事件之间的间隔"**（inter-event idle）——这本身是对的、是活性判定。
毛病只有一个：**它把"工具合法执行期（没 token 是正常的）"和"供应商真挂了（该有 token 却没有）"用同一个 300 秒、同一种结论对待。**

一场正经长会（`hold_meeting` 内部嵌套多次模型调用、几分钟不吐 token）走的是 `ToolCallStart → …几分钟… → ToolResultEnd`，中间合法不吐事件，却被算进 300 秒 → 顶爆 → 静默判"供应商断流"、就地收工 → 会没开完人被扔下。

这与业界一个著名同类 bug 同根：**计时器语义/挂载点错位**（LiteLLM #19909：stream_timeout 文档说"首 chunk 超时"，实现却挂在收到首 chunk 之后 → 2s 的超时 33s 才触发）。教训一句：**计时器度量什么、挂在哪，必须和它的语义对齐。**

## 二、① 最该抄的成熟范式（带出处）

四路调研收敛到**同一套范式**，都是生产级、非研究阶段：

1. **心跳/进度信号重置超时 + 硬上限双保险（协议级原话，最贴我们的纲）**
   MCP 官方规范：*"Implementations MAY reset the timeout clock when receiving a progress notification... however SHOULD always enforce a maximum timeout regardless of progress notifications, to limit the impact of a misbehaving client or server."*
   → 我们的流事件（ToolCallStart/ToolResultEnd/各种 Delta）**就是天然的 progress 信号**。收得到事件=心跳没停=别杀；无论如何留一个硬上限兜底防真死锁。
   出处：https://modelcontextprotocol.io/specification/2025-03-26/basic/utilities/progress

2. **两个独立的钟：idle-timeout（逐事件重置的空档）≠ total-timeout（整轮挂钟）**
   - httpx 四段超时里 `read=` 的定义就是"两个数据块之间最大空闲，每 chunk 重置"（inter-chunk idle），不是总时长。出处：https://www.python-httpx.org/advanced/timeouts/
   - LiteLLM 正式把超时拆成 `timeout`（整体）与 `stream_timeout`（等首 chunk/首 token，掐 hanging 供应商）。出处：https://docs.litellm.ai/docs/proxy/timeout
   - LangGraph 1.0 把机械超时拆成 `run_timeout`（硬墙，永不刷新）+ `idle_timeout`（进度重置，只在"停止可观测进度"时才烧）；"long-running but actively-streaming work doesn't trip it, but a truly hung call does"。出处：https://docs.langchain.com/oss/python/langgraph/fault-tolerance

3. **长任务保活的工业金标准：单次执行上限 ≠ 心跳间隔上限（Temporal）**
   长活动不靠总时长判死，靠"周期性 heartbeat"判活；收不到心跳=真死才重试，心跳照发=正经干活哪怕几分钟也不杀。铁律：**设了心跳超时就必须真在活儿里 heartbeat，否则该超时被忽略。**
   出处：https://temporal.io/blog/activity-timeouts

4. **"启动慢但合法"的豁免窗（K8s Startup Probe）**
   startup 没成功前 liveness 一律不执行、不许杀——正对应我们的"工具执行期"：工具没结束前，"供应商断流"这个死刑判定应被挂起。且 liveness 太激进会级联失败（官方警告）。
   出处：https://kubernetes.io/docs/concepts/workloads/pods/probes/

5. **判死前先探活，再判（Circuit Breaker 的 half-open + health probe，Nygard《Release It!》）**
   宣布供应商死之前，发一个廉价探针确认"是这条流卡了，还是整个供应商真挂了"。这正是船主要的"验证环节"。
   出处：https://resilience4j.readme.io/docs/circuitbreaker ；Nygard《Release It!》Timeouts + Fail Fast + Handshaking

6. **和我们一字不差的生产 bug + 已落地修复（最强背书）**
   openclaw #59946《Subagent killed by LLM provider streaming idle timeout (~60s)》：模型思考/长工具期间不吐 token，连接被静默切断，subagent 无报错无重试就死。修复已合入 commit `5451a87 feat: add LLM idle timeout for streaming responses`，并明确要求：①区分 'provider connection dropped' vs 'run timeout exceeded'；②completion event 必须带失败原因；③断连后至少重试一次。
   出处：https://github.com/openclaw/openclaw/issues/59946

**一句话范式**：把"一个机械总超时判死"升级成"**状态感知的 idle 超时（工具期豁免/放宽）＋ 整轮硬上限兜底 ＋ 触发后先探活再按类型大声报错**"。全部现成可抄，唯一要自己写的是"探活分类器"那几十行业务胶水（独一份）。

## 三、② 具体怎么改我们的 `唤醒本人` 流循环（可直接照改的设计）

### 改哪
- 文件：`工具/活_本人.py`
- 主改点：`唤醒本人` 的流循环（第 761–848 行那个 `while True`），把第 763 行那句 `wait_for(..., 300)` 换成状态感知版。
- 同步改点：`聊天唤醒` 的流循环（第 486–542 行），同法处理（聊天底盘几乎不开长会，但为一致性也走同一套判定函数）。
- 新增点：一个模块级"超时钟"配置常量 + 两个新函数（`_探活` / `_归类报错`）+ 一个显式异常类。

### 加什么（三段，直接照抄改）

#### A. 顶部配置：把一个 300s 拆成"三个钟"（替换第 17–19 行的 `模型流超时秒`）

```python
# ── 超时白箱化（2026-07-04 定稿，抄 MCP progress+硬上限 / LangGraph 双钟 / Temporal 心跳）──
# 单一 300s 的老账被拆成三个语义不同的钟：
模型产出空档秒 = 90.0     # STREAMING：模型"该吐字却不吐"的容忍。比原 300 更短更灵敏——
                        #   因为工具期已被单独摘出去，不再误伤，紧一点反而更早发现真死。
首事件等待秒 = 90.0       # AWAITING_FIRST：等首个流事件（掐 hanging 供应商，抄 LiteLLM stream_timeout 语义）
工具执行空档秒 = 900.0    # TOOL_RUNNING：一个长工具两次事件之间的容忍（开会几分钟够用）
整轮硬上限秒 = 1800.0     # HARD CAP：无论进度如何的整轮挂钟（MCP 铁律"SHOULD always enforce a
                        #   maximum timeout regardless"，防工具真死锁把整局挂住）
探活超时秒 = 15.0        # 判死前那次廉价探活请求自己的短超时
```

> 说明：这些是**起点值**，上线后按现场日志调（Temporal 经验：心跳间隔可远小于 start-to-close，越小发现越快）。工具期 900s 是给长会的宽限，不是缰绳；真死锁由 1800s 硬墙兜。

#### B. 状态感知的 idle 门控（替换现循环里第 761–771 行的取事件与超时分支）

核心：维护一个流状态 `态 ∈ {AWAITING_FIRST, STREAMING, TOOL_RUNNING}`；用现成的四种 Event 维护它（船主已点明"工具执行期可判"）；按状态选 idle 预算；叠一个整轮硬上限。

```python
import time
态 = "AWAITING_FIRST"
_起 = time.monotonic()
_上次事件 = time.monotonic()
while True:
    # 整轮硬墙（MCP 铁律：无论进度如何都有上限，防真死锁）——大声报，不静默
    if time.monotonic() - _起 > 整轮硬上限秒:
        await _关流(_流)
        raise await _归类报错(态, time.monotonic() - _上次事件, 整轮硬上限秒, hardcap=True)
    # 按状态选 idle 预算（TOOL_RUNNING 用大得多的宽限，正经长会不再被误杀）
    _预算 = {"AWAITING_FIRST": 首事件等待秒,
             "STREAMING": 模型产出空档秒,
             "TOOL_RUNNING": 工具执行空档秒}[态]
    try:
        ev = await asyncio.wait_for(_流.__anext__(), timeout=_预算)
    except StopAsyncIteration:
        break
    except asyncio.TimeoutError:
        # ★ 不静默收工：先验证（探活）再按类型大声报错（见 C）
        await _关流(_流)   # 抄 Agents SDK #2222：超时后显式 aclose，防取消传播坑
        raise await _归类报错(态, _预算, _预算)
    _上次事件 = time.monotonic()   # 收到任一事件 = 喂一次心跳，钟重置（wait_for 天然满足）

    # —— 用事件类型维护流状态（这就是船主说的"工具执行期可判"）——
    if isinstance(ev, ToolCallStartEvent):
        态 = "TOOL_RUNNING"
    elif isinstance(ev, ToolResultEndEvent):
        态 = "STREAMING"
    elif isinstance(ev, (TextBlockDeltaEvent, ThinkingBlockDeltaEvent)):
        态 = "STREAMING"
    # …（下面原有的 ModelCallStart/TextDelta/ToolCallStart/… 分发逻辑原样保留）…
```

辅助：
```python
async def _关流(流) -> None:
    """超时/判死后显式关掉底层生成器，避免取消传播坑（OpenAI Agents SDK #2222）。"""
    try:
        aclose = getattr(流, "aclose", None)
        if aclose:
            await aclose()
    except Exception:  # noqa: BLE001
        pass
```

> 注意一处真实细节：现循环里工具是**在流内执行**的（`ToolCallStartEvent` 后到 `ToolResultEndEvent` 之间就是工具在跑），所以"用事件维护 TOOL_RUNNING"零成本、天然可判——这正是船主原话"ToolCallStart 之后、ToolResultEnd 之前=工具在跑"。**注意并发工具**：一轮可能派多个工具（现代码 `_工具名` 是 dict 支持多 call_id）。稳妥做法是维护"未完成工具计数"，进 1 出 1，计数>0 即 TOOL_RUNNING：

```python
# 顶部：_在跑工具 = 0
# ToolCallStartEvent 分支里：_在跑工具 += 1；态 = "TOOL_RUNNING"
# ToolResultEndEvent 分支里：_在跑工具 = max(0, _在跑工具 - 1)
#                            if _在跑工具 == 0: 态 = "STREAMING"
```

#### C. 验证 + 报错：`_探活` 与 `_归类报错`（落船主"检测→带结果返回→终止→报错"）

超时不等于判死。先花十几秒对**同一供应商、同一 key、同一 model** 发一个极小请求探路，按返回把"不对劲"分类，带证据大声抛显式错误——取代原来万能的"供应商断流"。

探活客户端不去掏 agent 的私有 client（AgentScope 每次调用现造 `openai.AsyncClient`，没有稳定句柄）；改为**从花名册按岗位现造一个一次性探针客户端**——base_url/key/model 全和干活那台同源，最贴真实链路：

```python
# 显式异常（白箱：带 verdict + 证据，替代静默"供应商断流"）
class 供应商异常(Exception):
    def __init__(self, verdict: str, 阶段: str, 空档秒: float, 证据: str,
                 可重试: bool, hardcap: bool = False):
        self.verdict = verdict        # STREAM_STALLED_ALIVE / BILLING / RATELIMIT /
                                      # NETWORK / TIMEOUT / AUTH / GARBAGE / HARDCAP_DEADLOCK
        self.阶段 = 阶段; self.空档秒 = 空档秒
        self.证据 = 证据; self.可重试 = 可重试; self.hardcap = hardcap
        super().__init__(f"[{verdict}] 阶段={阶段} 空档={空档秒:.0f}s 可重试={可重试}：{证据}")


def _探针客户端(岗位: str):
    """按花名册现造一次性探针 client（base_url/key/model 与干活同源）。返回 (client, model)。"""
    import os, openai
    from 模型接入 import 花名册, _加载_env
    _加载_env()
    cfg = 花名册().get(岗位) or {}
    key = os.environ.get(cfg.get("key_env", ""), "")
    base = str(cfg.get("base_url", "") or "").rstrip("/") or None  # DeepSeek 留空=官方默认端点
    return openai.AsyncClient(api_key=key, base_url=base), cfg.get("model", "")


async def _探活(岗位: str) -> tuple[str, bool, str]:
    """判死前的验证环节：发 max_tokens=1 极小请求探同一供应商。
    返回 (verdict, 可重试, 证据)。全部走 OpenAI 兼容 SDK 的类型化异常，不做字符串瞎猜。"""
    import openai
    try:
        client, model = _探针客户端(岗位)
    except Exception as e:  # noqa: BLE001
        return "UNKNOWN", False, f"探针客户端搭建失败：{type(e).__name__}: {e}"
    try:
        r = await asyncio.wait_for(
            client.chat.completions.create(
                model=model, messages=[{"role": "user", "content": "ping"}], max_tokens=1),
            timeout=探活超时秒)
        if not getattr(r, "choices", None):
            return "GARBAGE", False, f"探活空返/乱返：{r!r}"[:400]     # 抽风
        return "STREAM_STALLED_ALIVE", True, f"探活正常({getattr(r,'id','')})"  # 供应商活着→是这条流卡了
    except openai.APITimeoutError as e:
        return "TIMEOUT", True, f"探活也{int(探活超时秒)}s超时：{e}"[:400]
    except openai.APIConnectionError as e:
        return "NETWORK", True, f"探活连不上（断连）：{e}"[:400]
    except openai.RateLimitError as e:
        # 欠费 vs 限流：都可能 429，但处理相反（退避对限流有用、对欠费无用）
        body = getattr(e, "body", None) or {}
        code = (getattr(e, "code", "") or (body.get("code") if isinstance(body, dict) else "") or "")
        txt = str(e)
        if (str(code) == "insufficient_quota" or "余额" in txt
                or "Insufficient Balance" in txt or "Arrearage" in txt or "1113" in str(code)):
            return "BILLING", False, f"欠费/额度用尽：{txt}"[:400]       # 不可重试，充值才行
        ra = ""
        try: ra = e.response.headers.get("retry-after", "")
        except Exception: pass
        return "RATELIMIT", True, f"限流（retry-after={ra}）：{txt}"[:400]
    except openai.AuthenticationError as e:
        return "AUTH", False, f"鉴权失败(401)：{e}"[:400]              # key 失效，不可重试
    except openai.APIStatusError as e:
        sc = getattr(e, "status_code", "?")
        if str(sc) == "402":
            return "BILLING", False, f"欠费(402)：{getattr(e,'response',None) and e.response.text}"[:400]
        return f"HTTP_{sc}", True, f"HTTP {sc}：{getattr(e,'response',None) and e.response.text}"[:400]
    except Exception as e:  # noqa: BLE001
        return "UNKNOWN", False, f"探活异常：{type(e).__name__}: {e}"[:400]
    finally:
        try: await client.close()
        except Exception: pass


async def _归类报错(阶段: str, 预算秒: float, 空档秒: float, hardcap: bool = False):
    """超时触发时的白箱出口：先探活，再带 verdict+证据抛显式异常。绝不静默判'供应商断流'。"""
    # 硬上限=工具真死锁，探活意义不大，直接带诊断报（但仍探一下给证据）
    岗位 = _当前岗位_var.get() or ""
    verdict, 可重试, 证据 = await _探活(岗位)
    if hardcap:
        return 供应商异常("HARDCAP_DEADLOCK", 阶段, 空档秒,
                        f"整轮超{int(整轮硬上限秒)}s硬上限，疑似工具真死锁；顺带探活={verdict}({证据})",
                        可重试=False, hardcap=True)
    return 供应商异常(verdict, 阶段, 空档秒, 证据, 可重试=可重试)
```

#### D. 循环外把异常翻成"白箱亮相 + 收口"（改现循环的 `except asyncio.TimeoutError` 分支所在层）

现在第 766–771 行是"超时→亮一句'供应商断流'→静默收工"。改成**捕获 `供应商异常`，把 verdict/证据/可重试亮给船主的窗户，再决定重试还是终止**：

```python
except 供应商异常 as e:
    _人话 = {
        "STREAM_STALLED_ALIVE": "供应商探活正常、是这条流本身卡住了",
        "BILLING": "供应商欠费/额度用尽（充值才行，重试没用）",
        "RATELIMIT": "被限流了（稍后退避重试）",
        "NETWORK": "网络断连（掉线）",
        "TIMEOUT": "供应商侧真超时/无响应",
        "AUTH": "密钥失效/鉴权失败",
        "GARBAGE": "供应商抽风（空返/乱返）",
        "HARDCAP_DEADLOCK": "整轮超硬上限，疑似工具死锁",
    }.get(e.verdict, e.verdict)
    _亮({"类型": "进展", "内容":
         f"{_人}的模型流在【{e.阶段}】空档 {e.空档秒:.0f}s——已探活验证："
         f"{_人话}。证据：{e.证据[:200]}"})
    完整.append(f"\n（模型流在{e.阶段}期停了：{_人话}。已探活验证，非静默判死。"
               f"{'可重试' if e.可重试 else '不可重试，需处理供应商'}。）")
    收口起 = 0
    停止了 = True
    break
```

> 重试策略（按 verdict，抄 OpenAI cookbook + openclaw 结论）：`STREAM_STALLED_ALIVE / NETWORK / TIMEOUT / HTTP_5xx` → 值得重试（openclaw：断连后至少重试 1 次）；`RATELIMIT` → 读 retry-after 退避后重试；`BILLING / AUTH / GARBAGE` → 立即终止大声报，不静默重试。**重试放在编排层**（办公室/派活那层）按 `e.可重试` 决定，`唤醒本人` 只负责"验证+亮相+带 verdict 抛/收口"，职责不混。

## 四、③ 诚实评估：哪些直接抄、哪些过度工程不必做

### 直接抄（成熟、低风险、对症）
- **状态感知 idle 门控（工具期豁免）** —— 根治误杀，就是 openclaw #59946 的官方解、有生产 commit。**必做。**
- **整轮硬上限兜底** —— MCP 铁律，防工具真死锁，一个减法就加上。**必做。**
- **超时后探活 + 类型化异常分类** —— 落船主"验证+报错"的核心，复用 OpenAI 兼容 SDK 现成异常类（APITimeoutError/APIConnectionError/RateLimitError/AuthenticationError/APIStatusError），不手搓字符串匹配。**必做。**
- **各厂欠费/限流对照判定**（DeepSeek 402/"Insufficient Balance"、百炼 Arrearage/Throttling.RateQuota、GLM 1113、OpenAI insufficient_quota）—— 我们正好四厂混用，这张表直接抄进 `_探活`。**必做。**
- **超时后显式 aclose 流** —— 抄 Agents SDK #2222 的取消传播坑，几行，**必做。**

### 可做可不做（有价值但非本次必须）
- **httpx 底层双保险**（给 AgentScope 的 model 传 `client_kwargs={"timeout": httpx.Timeout(connect=5, read=..., ...)}`）——`_openai_chat/_model.py` 第 167 行 `self.client_kwargs` 确实会透传给 `openai.AsyncClient`，天然可加。作为"网络层真断先由 httpx.ReadTimeout 兜底、我们的 watchdog 抓上层事件空档"的第二层防线，锦上添花。**建议做，但可二期**，因为它需要给 `建模型` 加一个 client_kwargs 通道，改动面比核心大一点。

### 过度工程 · 本次不必做
- **Temporal / 真正的 Circuit Breaker 状态机（pybreaker/resilience4j）** —— 那是跨进程、跨供应商长期熔断的重器。我们是单进程、单会话，已有"会话动作硬上限=200"这道费用闸兜底，再上断路器是拿大炮打蚊子。**不做**（其"探活后再判"的思想已被我们的 `_探活` 吸收，够了）。
- **MCP Tasks / dispatcher+checker 异步轮询把长会彻底摘出主流**（工具立即返回 task handle、主循环轮询 job_id）—— 这是终极解耦解法，但要重构会议室的执行模型，改动巨大。**本次不做**，记为未来可选升级；本方案的"工具期豁免"已让长会不被误杀，性价比够。
- **keepalive/heartbeat token 注入** —— openclaw 提的补充路线（让供应商周期性吐心跳 token）。我们的事件流已能当心跳用，不必再叠一层。**不做。**
- **把 idle 阈值做成每厂各一份的精细配置** —— 起步用统一值 + 现场调即可，别一上来就过度参数化。**不做。**

## 五、④ 需船主拍板的点

1. **三个钟的起点值**：模型产出空档 90s / 首事件等待 90s / 工具执行空档 900s / 整轮硬上限 1800s / 探活 15s。
   - 尤其"工具执行空档 900s"：这是给长会的宽限上限。你的会最长大概开多久？900s（15 分钟）够不够、要不要给到 1200s？
   - "整轮硬上限 1800s"（30 分钟）：这是防死锁的最后硬墙，会不会太松/太紧？

2. **探活要不要真花钱**：探活是一次 `max_tokens=1` 的真实请求（几乎不要钱，但确实打真接口、四厂都会被打一次）。认可"判死前花一次极小请求换白箱诊断"这笔账吗？（另一条不花钱的路是只 `client.models.list()` 判 402/429/连接错，但拿不到"抽风/空返"这类诊断——**建议用 max_tokens=1**。）

3. **重试的边界**：`STREAM_STALLED_ALIVE`（探活正常、就这条流卡了）到底重试几次？openclaw 的结论是"至少 1 次"。定 1 次还是 0 次（直接报给你、你手动决定重跑）？考虑到你反复强调过"闷头重试是机器行为"，倾向**默认 0 次自动重试、一律带 verdict 报到你窗户、由你/舟点重跑**——请拍板这条口径。

4. **改动落点确认**：核心改 `工具/活_本人.py` 的 `唤醒本人`；`聊天唤醒` 同步同一套判定函数；重试逻辑放编排层（办公室/派活）而非 `唤醒本人` 内部。认可这个分工吗？

5. **httpx 底层双保险（第四节"可做可不做"那条）**：要不要本期一并做（给 `建模型` 加 client_kwargs 通道），还是先只做事件层、二期再补？
