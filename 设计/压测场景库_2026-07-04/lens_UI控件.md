# 压测视角 · 前端逐控件 · 猴子测试（小到一个 UI）

**本视角总述**：这份清单是站在"破坏者"位置逐个 UI 控件去逼 bug 的——不是核对功能，是赌它在真实乱用/长期使用下崩在哪。每条都落到本仓库真实代码的具体机制（文件+函数+行为），四问贯穿：①能用吗 ②点开有没有问题 ③好不好看（深空全息军规：凡"底+框"皆廉价、结霜玻璃仅可读性豁免）④显示的是真的吗（假数据/假活人=理念破产）。已在通读中抓到一条真编译错误（`HallView.tsx:475` 的 `set入聊` 越界，`npx tsc --noEmit` 直接报 TS2552），单独立为 UI控件-01。产品即将上线，所以"活人感/同一性/记忆连续/真实性"崩了一律往 P0/P1 压。

### UI控件-01 · 会议浮层插话框：一点就崩（真·编译错误，构建直接挂）
- **视角/人群/攻击向量**: 普通用户点开一场进行中的会议，想在会场里插一句话——最普通不过的操作。
- **前置状态**: 公司正在开一场会（会议卡 live 态），用户点会议卡 → `MeetingOverlay` 展开、未结束分支渲染 `meeting-interject` 的 textarea。
- **操作步骤**: 鼠标点进"插话进会场"那个 textarea（触发 onFocus）。
- **健康的活公司应该**: 聚焦输入框、可以打字、回车插话进会场。
- **赌它会崩在**: `HallView.tsx:475` 的 `onFocus={() => set入聊(true)}` —— `set入聊` 是 `HallView` 的 prop，**根本没传进 `MeetingOverlay`**。`npx tsc --noEmit` 实测报 `TS2552: Cannot find name 'set入聊'`。Vite/esbuild 开发模式只剥类型不做类型检查，所以 dev 跑得起来但**生产 `tsc && vite build` 会失败**；即便硬跳过类型检查，运行时一聚焦就抛 `ReferenceError: set入聊 is not defined`，插话框整块崩。这是"即将上线"状态下的定时炸弹。
- **压到哪条圣域/宗旨**: 插话即到（三律之一）——会议插话是活人感的核心通道，它一点就炸；且会议室"自建成零场次"的已知账本一旦被真正打开使用，第一脚就踩雷。
- **崩了多严重**: P0（构建阻断 + 运行时崩溃）

### UI控件-02 · 打字机去重键把"隔时重发的同一句"误杀
- **视角/人群/攻击向量**: 真实人乱用——示例主人隔几分钟对公司重发几乎一样的一句话（"再看看那个文件"→过五分钟又"再看看那个文件"），或老钟这一轮的回复和上一轮巧合同一句。
- **前置状态**: 大厅在跑一个任务，`已播`（Set）里已经有键 `老钟|好的我来看`。
- **操作步骤**: 触发老钟再说一模一样的"好的我来看"（同一 run 内重复，或 SSE 重连重放）。
- **健康的活公司应该**: 该显示的显示、该去重的只去重"同一条被重放两次"。
- **赌它会崩在**: `hallStore.ts` 的 `已播` 用 `who + '|' + 内容` 当唯一键（line 190、265），**完全不带时间/序号**。SSE 重连整场重放要靠它挡双泡——但代价是：同一个人这一场里**真的说了两遍同样的话，第二遍被永久吞掉**，打字机里那句永远不出现。活人本来就会重复措辞，一被吞，用户看到的对话是残缺的（少一句），却毫无提示。这是"显示的是真的吗"的假阴性。
- **压到哪条圣域/宗旨**: 记忆连续/真实性——播出来的对话不等于真实发生的对话。
- **崩了多严重**: P1（伤真谛：呈现的对话被静默篡改）

### UI控件-03 · 字幕栈 2 分钟去重窗把"半小时后原话重发"照吞
- **视角/人群/攻击向量**: 长期使用——用户习惯性重复同一句指令，或打字机跨分钟播放。
- **前置状态**: 持久态 `hall.事件` 里有一条船主 04:45 说的"开始吧"，字幕栈 `stableTail` 取最后 20 条含它。
- **操作步骤**: 用户在 04:46、或 04:47 的窗口边缘再发一次一模一样的"开始吧"（临时气泡 t=播放时刻）。
- **健康的活公司应该**: 隔了时间的两次真实发送，都要各自出现。
- **赌它会崩在**: `HallView.tsx` `useDialogueStack` 的 `dedupedTemp` 判据：同人同句且 `|sMin - eMin| <= 2` 分钟就当双份丢掉（line 281-286）。注释自称"窗口2分钟既杀双份又不吞隔半小时重发"——但 `取分钟` 只解析 `HH:MM`，**丢掉了小时进位**（`23:59` 与 `00:01` 会算成 1438 分钟差没问题，但 `13:00`=780 与 `12:59`=779 差 1 会误判为同分钟段；更狠的是跨小时同分钟如 `12:01` 和 `13:01` → 720 与 780 差 60 不误杀，但 `12:01`/`12:02` 隔一整小时无法区分因为没有秒/日期）。真实后果：临时气泡的 t 有秒但被 `取分钟` 砍掉秒，跨分钟播放的正常单条也可能和历史里同人同句撞进 2 分钟窗被吞。
- **压到哪条圣域/宗旨**: 真实性——对话流可能少显示用户自己刚发的话。
- **崩了多严重**: P1（伤真谛/伤同一性感知）

### UI控件-04 · 滚动"只松不咬"死锁：打字机长文时永远追不回底部
- **视角/人群/攻击向量**: 猴子测试——用户在长回复流式打字时用触控板轻微上滑一下，然后就不动了。
- **前置状态**: 大厅在播一段很长的老钟发言，打字机每 25ms 追加字符、`ResizeObserver` 持续把内容撑高。
- **操作步骤**: 打字途中触控板往上滑一格（`onWheel` deltaY<0）→ `stickBottom.current=false`。此后不再碰滚轮，只看着。
- **健康的活公司应该**: 用户滑上去看历史时不打扰他；等他滑回底部附近自动恢复跟随。
- **赌它会崩在**: `HallView.tsx` 松粘底设计成"只松不咬，重新咬上只归用户的手（onWheel/发消息）"（line 144、133）。但打字机在**持续撑高内容**：`ResizeObserver` 回调里 `else set有新消息(true)`（line 81），于是"新消息"药丸疯狂闪、而 `onScroll` 里 `distance>=80` 反复把 `stickBottom` 按死。用户想靠"往下滚回底"自动重咬——可 `onScroll` 分支里 distance<80 时只 `set有新消息(false)` **不重置 stickBottom**（只有 onWheel 的 deltaY>=0 且 <80 才重咬）。触控板惯性/程序滚动都算 onScroll 不算 onWheel，于是出现"我明明滚到底了跟随却不回来"的死结，只能去点药丸。
- **压到哪条圣域/宗旨**: 体验——但发生在核心对话流，长期高频。
- **崩了多严重**: P2（体验，但高频刺痛）

### UI控件-05 · @选人器：中文输入法组词时上下键/回车吞字、候选空数组越界
- **视角/人群/攻击向量**: 中文用户用拼音输入法打 `@` 后按空格/回车、或候选为空时敲键。
- **前置状态**: 大厅空闲（非工作中），输入框已有 `@老`。
- **操作步骤**: (a) 输入法候选窗开着时按 ↓/↵；(b) 把 `@` 后面敲成谁都不匹配的 `@zzz` 再按回车。
- **健康的活公司应该**: 组词期不抢按键；无候选时回车就正常发送/换行。
- **赌它会崩在**: `HallView.tsx` line 194 `if (艾特候选.length > 0)` 分支内，ArrowDown/Up 直接 `e.preventDefault()` 抢键（line 195-204），**没判 isComposing**——中文组词时按上下选字会被选人器截走，字选不动。回车分支虽判了 isComposing（line 205），但 `选艾特(艾特候选[Math.min(艾特选中, 艾特候选.length-1)])`——当 `艾特词` 改变使候选**从有变无的同一帧**若竞态未及时更新，`艾特候选[...]` 可能 undefined 再 `.名` 抛错。且 `@zzz` 无候选时（`艾特候选.length===0`）回车走到 line 216 直接 send，把 `@zzz` 当正文发出去——用户以为在选人。
- **压到哪条圣域/宗旨**: 体验+真实性（点名/单聊语义靠 @，@ 不可靠则点名直通门形同虚设）。

### UI控件-10 · 记忆库删除/转正用整行原文当 key 和标识，同文两条一删删俩、含特殊字符匹配失败
- **视角/人群/攻击向量**: 真实管理——用户在记忆库删一条流水，或某人某天说了两遍同样的话被记了两行。

### UI控件-12 · 打字机播放泵与"待恢复"竞态：任务刚结束就发新消息，旧队列串进新对话
- **视角/人群/攻击向量**: 急性子用户——老钟报告一结束（run结束）立刻打下一句发送。
- **前置状态**: 上一个 run 刚 `resolve`，`待恢复.current=true`，播放队列里还剩两句没播完。
- **操作步骤**: 在播放泵还在吐字、`待恢复` 未触发时，用户回车发新任务。
- **健康的活公司应该**: 新任务干净开始，旧队列要么播完要么丢弃。
- **赌它会崩在**: `hallStore.ts` `智能发送` 新任务分支清 `播放队列.current=[]`、`已播=new Set()`、`待恢复=false`、`set临时([])`（line 141-144）。但 25ms 播放泵是**独立定时器**，清空和它并发：泵在同一 tick 可能刚 `shift` 出一句正 `set临时(l=>[...l,{流式...}])`（line 91），紧接着 `set临时([])` 与之竞争——React 批处理下顺序不定，可能出现旧句子的流式气泡插进全新的空对话里，或 `已播` 被清后旧队列若还没清完的一句重新可进队造成重播。更隐蔽：`根单元id/根名字` 是 ref 立即清，但泵引用的是队列快照，落款可能挂错人。
- **压到哪条圣域/宗旨**: 打字机"一次一人、人人平等"+真实性（谁说的话串台）。
- **崩了多严重**: P1（对话串台/落款错人，伤活人同一性）
