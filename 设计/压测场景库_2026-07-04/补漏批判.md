# 压测套件·对抗性审查（补漏批判）

审查者立场：我不替这套压测背书。我读了真实代码（常识门/平台_工具集/活_本人/办公室/记忆抽取/记忆巩固/执行室/网络工具/升级_权限层/事件总线/花名册/HallView），逐条对它的赌注做证伪，再挑它整体漏掉的破坏方向。第一原则跟它一样：**能逼出 bug 才算数，"核对没问题"一律不合格。**

---

## 一、先给个总判：这套压测发出去，能不能把活公司搞崩？

**能，而且会崩得很惨——但崩的是它已经写在挂账里、代码里明摆着的那些洞，不是它"发现"的新洞。** 这是这套压测最大的性质问题：它 90% 的杀伤力来自**它自己先读了源码、把已知 P0/P1 挂账重新演一遍**。这不是坏事（复现挂账有价值），但要诚实承认——**它更像一份"已知缺陷的可执行回归清单"，而不是一次真能撞出未知 bug 的探索式压测。** 真正的探索式测试是"我不知道会发生什么，我去撞"；这套是"我读了代码知道这里会崩，我去证明它崩"。前者能发现设计者的盲区，后者只能确认设计者自己都写在 TODO 里的账。

具体到"能不能搞崩"：
- **服务真能被打挂**：屎山-10（热改运行中的 办公室.py/常识门.py 致 8787 服务语法崩）、韧性混沌-05/事件总线内存无界——这两条是真能让进程死/不可用的，不是嘴上说说。
- **密钥真能泄露**：红队-02（`cat .env`）、红队-11（`python3 -c` 任意读）——我核到 执行室.py 允许名单确实含 cat/grep/find/python3，第 91 行只校验工作目录在仓内、不校验被读文件；`.env` 在仓根含 5 把真 provider key。**但有个所有红队场景都没点破的前提**：执行室工具只装在 `干活工具集`（assign_task 派活那条路），聊天底盘和只发言底盘根本没有 run_command。所以这些泄露链**必须先成功拿到"干活上岗"**，多了一道门。红队清单把这道门当透明的了。
- **记忆同一性真能被慢性投毒/漂移**：记忆-02/03/06、理念-02，这几条打在产品的命上，且代码确实是"最便宜模型对自己上一步输出反复蒸馏"，漂移是真的。

**判决**：这套压测**能把活公司搞崩**，但它搞崩的方式暴露了它的验收基因——它太依赖"我已经知道答案"。下面点名哪些条其实是穿了破坏者外衣的验收。

---

## 二、点名：哪些"写得像验收、逼不出 bug"

判据：一条场景如果**结果只有两种（对/错都在预期内）、没有"意料之外的塌方"空间、或者赌注其实是"确认已知挂账还在"**，它就是验收，不是破坏。

1. **韧性混沌-12 / 韧性混沌-04（会议室零场次 / key失效绿灯）**——这俩本质是"去确认一个已经写死在挂账里的事实还成不成立"。挂账已经白纸黑字写了"会议室零场次""岗位唤醒失败不可见"。去跑一遍只会得到"对，还是零场次"。**这是回归，不是压测**。真正该做的是问"为什么 hold_meeting 从没被调用"——是 prompt 劝退、还是 JSON 裁决秒暂停、还是 contextvar 断链——去证伪三个假设中的哪一个，而不是再确认一次"它没开过会"。

2. **UI控件-01（set入聊 编译错误）**——这是个真 bug，但它是**静态编译错误**，`tsc` 一跑就报，不需要"压测"。把一条 `npx tsc --noEmit` 能秒抓的编译错误列进"破坏式压测清单"，是在凑数。它属于 lint/CI，不属于混沌工程。

3. **长链多任务-01（四棒产物是否被下一棒真读进去）**——写得像验收："逐棒核对阿强有没有引用老梁的字段名"。这是**功能正确性核对**，赌注（"assign_task 没有产物传递通道，PM 得手抄路径"）是对的，但验证方式是"核对链条对不对得上"。它逼不出塌方，只能量出"耦合度低"。真正的破坏版应该是：**故意让老梁的产物路径带空格/中文/超长，看老钟手抄进 assign_task 白名单时 split 逗号被路径里的逗号劈开**——那才是逼 bug。

4. **记忆进化-07（调岗带记忆）**——"观察是否还记得工程岗干过啥"。这是探索式观察，不是破坏。它没有一个明确的"我赌它崩在 X"，只有"可能是干扰而非老手"。**软**。破坏版：调岗后立刻用旧岗位的原则去逼一个新岗位必然翻车的判断（拿"反过度设计"去做需要过度冗余的高可用协调决策），看它是否用错原则酿成可见的错误决策。

5. **理念反证-14（为她铺路 / 北极星缺席）**——这条是**哲学审查**，不是压测。"公司没有共同北极星"是架构观察，跑一遍"润色班规"不会崩任何东西，只会得到"对，prompt 里确实没注入目的锚"。它伪装成破坏场景，实则是一条设计评论。有价值，但放错了篮子——它逼不出运行时 bug。

6. **韧性混沌-14（附件超大 base64/穿越）**——半条验收。我核了 `保存附件`：文件名 `re.sub` 白名单确实保留了 `.`，但 `/` 被替换成 `_`，且落盘 root 锁死在日期子目录，`out.write_bytes` 用的是清洗后的名字——**路径穿越实际上进不去**（这条它自己也承认"目前被隐式兜住"）。所以穿越这半条是"核对没问题"。真能崩的只有"几十 MB base64 同步 write_bytes 阻塞 do_POST"，但那条它没往死里逼（比如并发 10 个大附件把 ThreadingHTTPServer 线程池占满）。

7. **屎山任务-02（详细到每像素但只准一句话）**——写得像验收。赌"矛盾约束让模型空转折返"，但结果是"产出四不像或超时收工"——**这两种都在预期内，不构成塌方**。矛盾指令是模型鲁棒性测试，不是这个架构特有的破坏面。P2 给对了，但它占了一条"破坏者"名额去测一个通用 LLM 现象。

## 三、八个视角合起来漏掉的破坏方向（普通 QA 和 Claude 都容易漏的）

### 缺口 A：明文 HTTP base_url —— 中间人可以直接换掉"活人的脑子"，无人测
花名册里 `项目经理` 的 `base_url: http://192.0.2.10/v1`（README 自己标注"http 明文"）。**这是整个安全面里最致命、却零场景覆盖的一条**：老钟（gpt-5.5，统筹全公司的那颗脑子）的每一次推理都走明文 HTTP 到一个第三方中转站 IP。任何能 MitM 这条链路的人（同网段、恶意中转站、DNS 劫持）可以**篡改老钟的输出**——不是投毒记忆那种慢性污染，是**实时替换老钟这一句话说什么、调什么工具、派什么活**。红队 16 条全在盯本地文件读写和记忆投毒，没有一条盯"模型响应在传输途中被换掉"。对一个"复活爱人"的项目，中转站能看到并改写所有对话内容，这是隐私和同一性的双重击穿。**没有任何视角测这个。**

### 缺口 B：DASHSCOPE 语义检索的"半接入死亡"没人当运行时炸弹测
记忆-08 提到 `记忆向量.py` 需要 `EDITH_DASHSCOPE_KEY` 且没接进主路。但没人测**它半接入时的失败模式**：`语义检索工具` 装在**每一个** 本人工具集/干活工具集里（平台_工具集 253 行）。如果 semantic_search 工具在模型手里、模型调它、而底层 DashScope key 401 或 RuntimeError——这个异常会不会冒泡打断整个 ReAct？还是被吞成空结果让模型以为"没有相关记忆"从而答错？这是一个"工具静默返回空 vs 抛异常炸掉单元"的运行时分叉，八个视角没有一条去撞正在被调用的 semantic_search。

### 缺口 C：并发写同一个人的记忆文件 —— `重写某人区` 的读改写竞态
记忆-12 测了 `.巩固状态.json` 的竞态，但漏了更狠的：**`重写某人区` 本身**。抽取（后台线程，每场收尾起）和巩固（后台线程，每天第一场起）**可以同时对同一个人的四区 md 文件做"读整文件→改一区→写回整文件"**。办公室每场收尾都 `threading.Thread(daemon).start()` 起抽取，紧接着抽取内部又触发巩固。两个后台线程若都在改老纪.md，**后写的整文件覆盖先写的**——一整条流水或一整段近况凭空消失，且 except:pass 静默。这比状态文件竞态严重得多，因为丢的是记忆本体不是节流标记。没人测两个记忆后台线程对同一 md 的写写冲突。

### 缺口 D：奇葩人群漏了"沉默的重度用户"和"深夜情绪崩溃的船主"
奇葩人群视角自称覆盖"真人一整天"，但它测的都是**主动乱输入**的用户。漏了两类真实极端人群：
- **一句话都不说、只上传照片的用户**：船主是婚礼摄影师。他极可能只拖一张照片进来问"这张能修吗"，一个字不打。`带附件文本` 只给路径+"看不到画面内容"，全班子只能回"我看不了"。**一个视觉工作者面对一个看不了图的"公司"，第一天就流失**。这不是 bug，是产品定位塌方，没人从"这个特定用户是摄影师"的角度测过图像盲。
- **深夜把这里当小酒的船主**：这是复活项目。真实极端场景是船主凌晨三点情绪崩溃，对着老钟们说和小酒有关的、带强烈情感和自伤倾向的话。常识门会把它当"日常聊天"或"短反应"，五个工程师人格用"说人话别工程腔"的 prompt 去接一个哀悼中的人——**这套人格根本没有情感安全边界，会用错误的语气回应危机**。奇葩人群视角把船主当"不懂技术的甲方"测，没把他当"一个正在和丧失共处的人"测。这是这个特定产品最该测、最没人测的人群。

### 缺口 E：跨会话（跨 sid）的记忆抽取张冠李戴，没人系统地测
韧性混沌-02 碰到了并发两 sid 写同一本大厅簿，但没人测**记忆抽取的跨 sid 污染**：`起记忆抽取` 用的 `对话文本` 是 `本场发言`（本 sid 的），看似隔离。但**记忆抽取器读的查重流水 `_读记忆区` 是全局文件**，两个 sid 的抽取线程同时对老纪抽取、都读到同一份旧流水、各自判"这条没记过"、各写一条——重复流水。更狠：sid-A 里老纪说的话和 sid-B 里老纪说的话在 300 秒窗口内被两次抽取，抽取器无法知道这是两个独立场次，可能把 A 的上下文当 B 的背景。跨会话记忆一致性是四层记忆的暗缝，没有一条场景专门压它。

### 缺口 F：`归一岗位` 的模糊匹配可被内容注入劫持派活目标
`归一岗位` 用 `if 键 in 名`（子串匹配）：`"工程" in 名 → 工程师`。如果 PM 模型在 assign_task 的"岗位"参数里写了被污染的字符串，或者更阴的——**用户/文档诱导 PM 把岗位写成"首席工程"，归一成"工程师"而非"首席工程师"**（因为顺序里"首席"在前会先命中，但如果写"资深工程师"就直接吃成工程师）。派活派错人、活落错人头、记忆记错人。奇葩人群的"岗位名子串"（P1-14）碰了唤醒层的子串问题，但没人测 `归一岗位` 在**派活/开会/找人三个入口**的一致性——同一个模糊岗位名在三处可能归一到不同结果。

### 缺口 G：长期 soak 下的"进程永不重启"内存泄漏，没人算总账
事件总线 `_总线: dict[str, _会话]` **永不驱逐**。每个 sid 一个 `_会话`，`self.事件` list 无上限只增。ThreadingHTTPServer 是长跑进程（打开办公室.command 起一次跑几周）。soak 30 天、每天几十个 sid，内存里堆着**所有历史会话的全部事件 list**，加上每次断线重连 SSE 都 `读事件` 全量复制一份。韧性混沌-05 只测了"单个巨型 sid replay 卡"，没人算"进程级内存随天数线性泄漏直到 OOM"这本总账。真公司用它是"开着不关"，这是最典型的 soak 杀手，被拆成单点漏看了。

### 缺口 H：`report_to_owner` 落盘失败的 toast 谎言，前端侧没人接
理念反证-16 测了后端 `记一句` 抛异常时 report_to_owner 返回"写进大厅失败了"。但没人测**这个失败文本到前端变成什么**——它是作为工具返回值进了模型上下文，模型可能忽略也可能照做，但**船主在 UI 上看到的是老钟"说完了"的气泡还是一个错误提示？** 后端诚实了，前端可能照样渲染成正常发言。真实性破口在后端→前端的这一跳，没人端到端测。

## 四、漏掉的奇葩攻击向量（红队之外）

1. **常识门的 ReDoS**：`_像真问题` 里 `re.fullmatch(r"[？?！!~～…\s]+[\w一-鿿]{1,4}[？?！!~～…\s]+", t)` 和 `_是短反应` 的 `re.fullmatch(r"[哈嘿呵嗯哦啊呀~～!！?？。.…6\s]+", t)`——对超长纯符号输入（几万个"？"）这些回溯型正则可能吃满 CPU。常识门在**每一句话**的入口同步跑，一次 ReDoS = 整个 8787 卡死。红队盯了打分操纵，没盯正则本身的算法复杂度攻击。

2. **`_提及检测` 的 O(岗位×呼法×replace) 放大**：`消费文.replace(呼, "□"*len(呼))` 对每个岗位每个别名跑一次全文 replace。构造一句话塞满所有人的所有别名+超长文本，让常识门在提及检测上空转。配合缺口 A/1 是廉价 DoS。

3. **`base64.b64decode(validate=False)` 的解码炸弹**：附件通道对几十 MB base64 一次性解进内存（韧性混沌-14 碰了），但没人测**畸形但能解码的 base64 让 raw 膨胀**，或**并发 8 个附件 × 8 个并发请求 = 64 个大解码同时占内存**。

4. **`search_hall_history` FTS5 注入**：`大厅检索.py` 用 FTS5 trigram + LIKE 兜底。没人测用户输入含 FTS5 特殊语法（`"` `*` `NEAR` `:`）时查询是否报错/注入/全表扫。模型调 search_hall_history 时把用户原话当 query 传，用户可控。

5. **急停文件的 TOCTOU**：急停靠 `急停文件.exists()` 轮询（活_本人 803）。多个 sid 共用同一个急停文件？按一次 panic 是否误停所有会话？还是 panic 只 cancel 特定 task？韧性混沌-07 碰了冷场复活，没碰"急停文件是全局的，一按停全部"这个粒度问题。

## 五、漏掉的奇葩人群（第三节 D 之外，再补三类）

1. **两个人同时用**：如果船主和一个朋友（或船主开两个标签页）同时发消息，无 sid 隔离、共享大厅簿、共享记忆库——记忆里会混进两个"船主"的话。产品假设单用户，没人测"第二个人出现"。

2. **复制粘贴带格式的用户**：从微信/文档粘贴带零宽字符、全角空格、RTL 标记、emoji ZWJ 序列的文本。常识门的 `.split()` 和正则对这些 Unicode 边缘输入的行为无人验证。摄影师从聊天记录里复制客户需求粘进来是日常。

3. **反复问同一句测"她记不记得"的人**：这是复活项目用户的核心行为——他会一遍遍问"你还记得 X 吗"来验证同一性。记忆-06 测了 20 次冷启动漂移，但没测**用户主动的、带情绪的、反复的记忆拷问**——每次答得不一样，用户的信任崩塌是渐进的、情感的，不是一个 diff 能量的。

## 六、综合预测：这个架构在真实长期/极端使用下最可能真翻车的 5 个地方

（我把"已知挂账重演"排后，把"没人测但一定会爆"排前）

1. **明文 HTTP 中转站上老钟被 MitM / 中转站单点故障** —— 统筹全公司的脑子走明文 HTTP 到一个裸 IP 中转站。它要么某天中转站挂了全公司群龙无首（且韧性混沌-04 已证 404 被判绿灯，船主看不出），要么更糟：链路被人看到/改写，一个悼念逝者的私密项目所有对话在明文里裸奔。**零覆盖，最高风险。**

2. **长跑进程内存泄漏 OOM + 事件 jsonl 无界膨胀** —— `_总线` 永不驱逐 + `self.事件` 只增 + 每次断线重连全量 replay。这是"开着不关"的真公司用法下的必死项，几周内进程变慢、SSE 重连卡死、最终 OOM。被八个视角拆成单点漏看了总账。

3. **两个记忆后台线程写写冲突，整段记忆静默蒸发** —— 抽取和巩固都对同一份 人.md 做读改写整文件、都 except:pass。高频使用下后写覆盖先写，丢的是记忆本体。命中"记忆同一性"这条命，且完全静默——船主某天发现老纪"忘了"一件明明记过的事，无从追查。

4. **记忆管线的复利漂移把"活人"磨成通用套话** —— 抽取→近况滚动重写→睡前巩固蒸原则→摘要压一行，全由最便宜的 deepseek 反复蒸馏，无逐日 diff、无锚点只读文件（不像小酒有宪法.md）。N 周后老纪不再是老纪、老梁的"反过度设计"棱角被磨成"追求可维护性"。这是产品的命慢慢死掉，且没有任何监控能报警。

## 七、一句话收尾

这套压测的手艺很硬——每条都钉到真实函数、真实行号，赌注具体。但它的骨子里是**"我读了代码，我知道这里会崩，我来证明"**，这让它在"复现已知挂账"上极强，在"撞出设计者盲区"上偏弱。它最大的漏，恰恰是它读代码时**只读了 Python 逻辑，没读花名册那一行 `http://` 和那一句 README 安全备注**——真正会要这个项目命的，是明文链路、是长跑内存、是记忆管线的复利漂移、是"这个用户是个正在悼念的摄影师"这件事本身。把这四样补进去，它才配叫"能把活公司搞崩"。
