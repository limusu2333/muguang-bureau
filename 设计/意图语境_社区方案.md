# 语境依赖意图 · 社区方案推荐（给船主）

> 船主令（这轮的纲）："看社区最新最热最好的方法，别闭门造车。"
> 场景：AI 陪伴群聊里，同样五个字"你们在干嘛"——前面聊得顺=招呼，前面刚惹烦=不满/跑偏。意图相反，只由对话流决定。
> 当前（错误）做法：一张招呼词典硬判（`活_本人.py:_像招呼`），见"在干嘛"就当招呼→只给最新 1 句上下文→模型读不出这是不满，去汇报旧进度。
> 四路独立调研，出处不同，**结论高度一致**。本文只做综合与落地，不重复四路原文。

---

## 一句话结论（船主先看这个）

**病根不是"词表调不好"，是"用词当决策变量"选错了。** 同样五个字词表特征恒定、意图却由对话流翻转，所以**词表在原理上分不开**——不是加词能救的，越加越串。

社区 2024–2026 的公认破法是：**把决策变量从"这个词是不是招呼"换成"这句话依不依赖前文"**（is_reaction / self-contained）。换了这个变量，两难自动消失——因为"依不依赖前文"本身就定义了"该给多少上下文"，同样五个字在顺境/逆境里这个值恰好相反，判定驱动、不由词表驱动。

**我们几乎零改动就能上**：现成的真多轮消息数组 + embedding/FTS 记忆，正是这套方案要的两个前提。把 `_像招呼` 那条硬判分支，换成一次"关系/自足性判定"的 LLM 调用即可。

## ① 社区最新最好的公认做法是什么（带出处）

四路调研落在**同一个范式家族**，只是叫法不同。按"离我们最近、最能直接抄"排序：

### A. 上下文感知的满意度/repair 判断器（最有说服力的反面教材+换代方案）
- **ACL COLING 2025 Industry《User Frustration Detection in Task-Oriented Dialog Systems》** — 他们线上原来跑的**正是关键词表**，实测精确率 100%、**召回率只有 1%**。原文结论：不满是通过**对话模式**（重复提问、否定、任务没解决、上文没被采纳）体现的，**而非脏话/负面词**。"你们在干嘛=不满"属于隐含不满，**词表结构性地抓不到**——跟我们现在的病历一模一样。
- 换代方案：把最近 N 轮**完整对话**（带 `USER:/SYSTEM:` 前缀）喂给一个轻量 LLM，任务说明里明确列出"不满不一定带负面词"，输出二元标签，F1 相对提升 16%，GPT-4o/Llama 都能到 ~86%。他们明确对比过"只喂最后一句"，结论 **full context substantially better**。
- 出处：https://aclanthology.org/2025.coling-industry.23.pdf ; arXiv 2411.17437

### B. 查询/意图改写门（IBM 生产在跑，最可逐字抄）
- **IBM Granite 3.2/3.3 Query Rewrite intrinsic**（已在生产 RAG 库发布）。判据原话可逐字抄：把用户最后一句改写成"**不需要前文就能理解其意图**"的单句；**若已自足则原样透传，不硬改**（selective rewriting）；输出 JSON。这正好是"一步判定同时决定给多少上下文"。
- 学界主流 **CQR（Conversational Query Rewriting）** 与它一致：把多轮降维成 self-contained standalone query。2025《Decontextualizing User Questions》(arXiv 2507.04884) 直接用大模型做统一改写器：判依赖→需要则改写→已自足则原样保留，**不用单独训分类器**。
- 出处：https://huggingface.co/ibm-granite/granite-3.2-8b-alora-rag-query-rewrite ; arXiv 2504.11704 ; arXiv 2507.04884

### C. 两阶段路由 + 用户回合关系 taxonomy（production 共识）
- **Stage-1 关系判定**：固定喂最近 3–5 轮（**不是 1 句，也不是全量**），只输出"当前句↔上一轮"的关系标签 + `is_reaction` 布尔。**Stage-2 上下文装配**：招呼/全新=只带最近 1–2 句；追问/纠正/不满=带上被指向那一轮完整内容 + 记忆召回。
- 关系 taxonomy 抄 **EMNLP 2025《User Feedback in Human-LLM Dialogues》**：Positive / Rephrasing(隐含不满) / Make-Aware±Correction / Ask-Clarification / No-feedback，多标签优先级 纠正>指错>要澄清>改述。
- 理论骨架抄 **ACL 2025《Do LLMs Understand Dialogues?》**：Dialogue Act 的 **backward-looking（回指过去=对上一轮的反应）vs forward-looking（开启新话题/招呼）** 二分。"词表分不开、关系能分开"的根因就在这。
- 出处：EMNLP 2025 arXiv 2507.23158 ; ACL 2025 https://aclanthology.org/2025.acl-long.1271.pdf ; Shopee/SUTD production MTIC arXiv 2411.12307

### D. 方向①"总是给足上下文 + CoT 让模型自己判"（最省改动的一条）
- **COLING 2025《LLM ContextBridge》**（用对话历史消歧意图的 hybrid）+ 2026 CoT intent 实践：CoT "particularly useful for distinguishing utterances with similar wording but different intents"。不预分类砍窗口，而是**把最近多轮真历史全给模型、用一步推理让它先想"这句依赖前文吗"再定意图**。
- 配套：把检索出的旧记忆**单独分区、打上"[背景·仅供参考]"标签**，与当前轮真消息物理隔开——直接堵"串味=被答成汇报旧话题"。
- 出处：https://aclanthology.org/2025.coling-industry.66.pdf ; Contextualizing Search Queries arXiv 2502.15009

**四路的公约数**：不给不同的词配不同上下文；而是**把"这句相对上文是新意图还是反应/是否自足"当成一个读完整对话流的判断题**，再由这个判断结果决定给下游多少上下文。

## ② 怎么破"招呼少上下文 vs 语境反应多上下文"的两难（关键）

**两难的根子：决策变量选错了。** 我们现在用"这句是招呼还是语境型"当分叉，而这个变量**恰恰是词表分不出的**（同样五个字）。于是招呼和不满被同一个词触发同一条窄窗口分支，永远分不开。

**破法：换一个能判出来的分叉变量——`is_reaction`（这句相对上一轮是 forward 开新 还是 backward 回指/反应）/ 等价的 `is_self_contained`（脱离前文能不能读懂它的意图）。**

关键洞察（四路一致）：**"多上下文"不是把一堆 history 丢给下游模型让它猜，而是"判定层集中吃上下文、装配层按判定结果给量"。**

三步，直接落到我们的真多轮消息数组：

1. **判定层：固定喂窗，别喂 1 句也别喂全量。** Stage-1 恒定取最近 **3–8 轮** role-annotated 消息（谁说的必须标——见下方硬提醒），这一步窗口大小**对所有句子一样**，从根上消除"招呼要少、语境要多"这个自相矛盾的前提。

2. **判关系/判自足，不判招呼。** 让判定 LLM 只输出一个 JSON：`{relation, is_reaction, points_to_turn_id}`。
   - "你们在干嘛" + 前文顺 → `is_reaction=false`（招呼/开新）
   - "你们在干嘛" + 前文刚惹烦 → `is_reaction=true, points_to=惹烦那轮`（回指=不满/纠正）

3. **装配层：量由后验决定。**
   - `is_reaction=false`（招呼/新意图）→ 只给下游最近 1–2 句，**不召回旧话题、不汇报进度**（天然不串味）
   - `is_reaction=true`（不满/纠正/追问）→ 把 `points_to` 那轮完整拉出 + embedding/FTS 召回，下游才读得出"这是冲着刚才那事来的"

这样"招呼少上下文、语境型多上下文"**不再是先验要猜的两难，而是判出 `is_reaction` 后自动得到的结果**。同样的词、相反的上下文，由判定驱动。

**硬提醒（ACL 2025 实证，必须知道，直接反驳我们现在的做法）：**
- **nearer-utterance bias**：LLM 严重偏向只看最近一两句——**我们现在只喂 1 句正好人为放大这个偏置**，"不满(backward)"必然读不出。
- **backward-looking bias**：盲目多给，模型又会把招呼也误读成回指过去。
- 所以要给的是**"结构化的对"，不是"更多的句子"**；且判定 prompt 里**必须 role-annotate 每一轮**（小北/小咪/船主分别说的）——LLM 判 backward/forward 严重依赖说话人角色，不标角色，"你们在干嘛"里的"你们"指谁都对不上。**我们代码已经在做这件事**（见 `构造聊天消息` line 496–503，把"谁说的"写进内容本身），这是加分项。

**兜底规则（抄 Intent-Mismatch 论文，治我们这个痛点最直接）：**
> "If the user has not explicitly approved the previous solution, he is not satisfied."
落成逻辑：若上一条是 AI 的方案/汇报，且用户这句**没有任何显式认可**（好/对/继续/谢谢…），则把"对上一条不满"的先验调高——哪怕字面像招呼，也优先澄清"你是觉得刚才没到位吗"而**不是默认汇报旧进度**。

## ③ 落到我们代码，最省改动的做法（可照抄设计）

现状（`活_本人.py`）：
- `_像招呼(句)` (line 135)：纯词表判当前一句。`"在干嘛"` 在 `_招呼词`(line 131)，永远命中→招呼→窗口=1。**这是病根。**
- `_判话题边界(最新句, 历史句子)` (line 144)：①词表直判→窗口=1 ②embedding 漂移→窗口=3 ③fail-safe→窗口=30。
- `构造聊天消息(岗位, …, 窗口=30)` (line 483)：窗口控制装配几句。
- `聊天唤醒` (line 543)：先判边界拿窗口，再 `构造聊天消息`。

**最小改动路径：`_判话题边界` 的"关系判定"这一层，用一次判定 LLM 调用替掉词表直判；`聊天唤醒` 的装配分支保持不变（它本来就是"按判定结果给窗口"，架构天生适配）。**

### 改法 A（推荐首选 · 判定门，改动最集中）

保留 `聊天唤醒`→`_判话题边界`→`构造聊天消息` 的三段骨架不动，只把 `_判话题边界` 的第一层换掉：

```python
# 治的病：_像招呼("你们在干嘛") 永远命中→窗口=1→读不出不满。
# 换：判定变量从"是不是招呼词"换成"is_reaction（相对上一轮是回指还是开新）"。
# 判定门恒定喂最近 N 轮 role-annotated 消息（不是1句、不是全量），输出结构化标签。

_判定窗口 = 6   # Stage-1 恒定喂窗：够覆盖"前面顺/刚被惹烦"的近况，别1句别全量

_判定指令 = """你在读一段 AI 陪伴群聊的最近几轮，参与者角色已标注（实例主人=船主/老板，其余为公司里的 AI 岗位同事）。
判断【实例主人最后一句】相对上一轮是什么关系，只输出 JSON，别的都不要说。

relation ∈ {
  greeting     : 招呼/寒暄/问近况，与上轮无未决牵连
  new_request  : 全新意图，与上轮无关
  follow_up    : 在上轮基础上追问/深化
  re_attempt   : 让重做上轮同一件事
  complaint    : 对上轮不满/指出你们跑偏/要求纠正
}
is_reaction    : 这句是在【回应/评价上一轮】(true) 还是【开启新话题】(false)
points_to      : 若 is_reaction=true，它冲着哪一句（给该句在下面列表里的序号，从0起）；否则 null

判据：看这句是【回指过去】(backward→多半 reaction) 还是【塑造后续】(forward→多半 greeting/new)。
注意：'你们在干嘛''在忙啥''怎么样了'这类**表面像招呼**，但若上一轮刚让船主不满、或船主上一条没有显式认可(好/对/继续/谢谢)你们的方案，它极可能是 complaint，别默认当招呼。
不满往往**不带负面词**——重复提问、否定、任务没解决、上文没被采纳，都是信号。

输出：{"relation": ..., "is_reaction": ..., "points_to": ...}"""


async def _判话题边界(最新句: str, 历史句子: list[str]) -> tuple[bool, str, int]:
    """判「最新句」相对上文是招呼/新意图(开新)还是反应/不满(回指)。
    返回 (是否只带少上下文, 白箱依据, 建议窗口)。
    新变量=is_reaction；不再用招呼词表当判据（词表对'你们在干嘛'恒定命中、分不开顺/逆境）。"""
    if not 最新句:
        return False, "无船主句→保守当接续", 30
    try:
        判 = await _判定LLM(最新句, 历史句子[-_判定窗口:])   # 见下
        r = 判.get("relation"); react = bool(判.get("is_reaction"))
        if not react:
            # 招呼/新意图：只带最新1-2句，不召回旧话题、不汇报进度（治串味）
            return True, f"判定={r}/开新→少上下文", _招呼窗口
        # 反应/不满/追问：多带上下文（被指向那轮 + 记忆召回在装配层做）
        return False, f"判定={r}/回指→带上下文", 30
    except Exception as e:  # noqa: BLE001
        # fail-safe：判定不可用时保守当接续、不丢上下文（宁可多给也别把不满读丢）
        return False, f"判定不可用({type(e).__name__})→保守当接续", 30
```

`_判定LLM`：复用本地 Gemma + llama.cpp，约束 JSON 输出（我们 `MNABoXingZhaiYao` 那套 schema 经验现成）。喂进去的是 role-annotated 消息——**直接借用现成的 `构造聊天消息(岗位, 历史记录=…, 窗口=_判定窗口)`**，它已经把"谁说的"写进内容（line 496–503），拿来当判定门的输入零成本。

**注意语义反转**：现有 `_判话题边界` 返回的第一个布尔叫"是新话题"，装配用它选小窗口。改法里它的含义变成"是否只带少上下文（=开新/招呼）"，逻辑一致（开新→少、回指→多），`聊天唤醒` line 543–546 那段几乎不用动，只把 progress 文案里的"新话题"改成"招呼/开新 vs 承接不满"。

### 改法 B（备选 · 改写门，IBM Granite 逐字抄）

若想更贴 RAG 检索：不判 relation，而是判**自足性**，一步把上下文 in-line 进单句 query：

```
逐字抄 IBM Granite 指令（放进本地 Gemma 的 rewrite 角色）：
Reword the final utterance from the USER into a single utterance that doesn't need
the prior conversation history to understand the user's intent. If the final
utterance is a clear and standalone question, please DO NOT attempt to rewrite it,
rather output the last utterance as is. Output JSON: {"rewritten_question": <REWRITE>}
```
- 自足（前文顺）→原样输出→只给这一句、不检索记忆、不汇报。
- 不自足（前文惹烦）→改写器把矛头/情绪补进去（"你们又跑偏了，我不满，到底在干嘛"）→拿这句去打 embedding/FTS→进对话链。**多上下文被改写吃进单句，不把整段 history 丢给下游**（避免串味）。
- 针对"不满"加一句（RECAP 思路，需小样本验证）：`...If the user is expressing dissatisfaction or implying the team went off-track, make that explicit in the rewrite rather than treating it as a literal greeting.`

**A vs B 选择**：A 改动更集中（只换 `_判话题边界` 内层、装配骨架不动），且直接产出"带哪一轮/是否召回"的路由信号，**推荐 A**。B 更适合把上下文塞进检索 query 的场景，可作为 A 内部"装配 is_reaction=true 分支时"的召回 query 增强，二者不冲突。

### 装配层加固（两个改法都要，堵串味的机制层解法）
`构造聊天消息`/`_聊天系统提示` 里，把 embedding/FTS 召回的旧记忆**单独成块、前置标注**：
> `[以下为检索到的历史背景，仅供理解船主时参考；除非船主主动追问，不要主动复述或汇报这些旧内容]`
与当前轮真消息物理隔开（方向③，COLING/Anthropic 长程 Agent 实践同构）。

## ④ 诚实：成熟直接抄的 vs 过度工程别做的

### ✅ 成熟可直接抄（2024–2026 production 共识，多篇工业界论文+产品佐证）
1. **把词表降级/删掉，判定变量换成 is_reaction / self-contained** —— 这是四路唯一公约数，直接抄。
2. **两阶段路由（判关系 → 按关系装上下文）** —— Shopee/Google production 在跑，抄 JSON schema 和判据表。
3. **判定门恒定喂 3–8 轮 role-annotated 消息** —— 我们 `构造聊天消息` 已经在做角色标注，白捡。
4. **IBM Granite 改写门那句原话 + JSON 契约 + selective rewriting（已自足则原样透传）** —— IBM 生产、LangChain 生产都在用，逐字抄。
5. **"未显式认可即视为不满"兜底规则** —— 一句 prompt，马上抄进去当先验，不用上任何架构。
6. **旧记忆分区 + "[背景·仅供参考]"标签** —— 一个标签，直接堵串味。
7. **判定用便宜/毫秒级调用挂每轮**（2026 产品共识：LLM-as-judge 太慢太贵不每轮跑）—— 我们用本地 Gemma 正好便宜，符合。

### ⚠️ 成熟但要自己标定/小样本验证（别照抄数字）
- **判定窗口 N**（3–8）、**招呼窗口保留几句**、**CoT 指令的中文措辞**、**"不满"识别加的那句 prompt** —— 都要在**我们真实群聊语料**上小样本试跑校准，别照抄英文论文的数字。这符合舟的查证纪律：抄范式与出处，不抄具体数值。
- **backward/forward 二分概念成熟，但 LLM 有 nearer-bias/backward-bias 两个坑** —— 靠"固定喂 3–8 轮 + role 标注 + few-shot 例子"压制，上线后要看 badcase。

### ❌ 过度工程 / 别做（现在别碰）
1. **别再往招呼词典加词** —— 被词表天花板锁死，越加越串。这是要删的病根，不是要优化的模块。
2. **别叠"该不该检索"的脆弱特征分类器** —— arXiv 2603.13301《Not All Queries Need Rewriting》实证：纯检索-词汇层自动判"该不该改写"AUC 仅 0.593，gated 策略没显著赢过"从不改写"。检索决策**就由 is_reaction / self-contained 那一位带出来**，别再叠一个二次门控。
3. **别急着上 DPO 微调改写器 / RECAP 训练版**（arXiv 2509.04472）—— 效果好但要训练。先用 prompt 版改写跑通，别上微调。
4. **别上状态化情绪漂移追踪**（DeepContext arXiv 2602.16935）—— 研究阶段。留作后续给"前面惹他烦"加一个显式情绪状态位的加固点，现在不必上。
5. **别无脑堆全量上下文** —— arXiv 2510.17940 / 2606.09900 双双证明精挑 bounded 上下文常比全量更准更省（9.6k tokens 胜 79k full-context）。"总是给足"指给足**判定门那 3–8 轮**，不是把所有历史塞给下游。
