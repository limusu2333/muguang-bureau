【BUG-001】who_is_free 查不出"无法唤醒"，把限额卡死的人显示成"空闲在线"

- 始末：2026-08-29 18:50 船主问谁在线 → 18:50-18:51 老梁两次依据 who_is_free 报"老钟在线、空闲" → 19:14/19:19 船主指出老钟因中转站限额实际无法被唤醒，代理经理租约本身就是因其缺席才触发 → 19:19 老梁认错。
- 现象：老钟因中转站限额无法被唤醒，who_is_free 仍显示其"此刻空着(没在跑任务)"；值席据此向船主误报"老钟在线"，并替无法出声的人说话。
- 根因：考勤板只记录"唤醒本人"期间的上工/下工打卡，"空闲"＝花名册全员−在跑任务者；唤醒失败（中转站限额/429/AccessDenied等）不在考勤板留任何状态，"没在跑任务"与"能出来"被混为一谈。
- 关联代码/文件（相对公司根目录）：
  - 工具/工具间.py：_在岗、上工()、下工()、在岗快照()、查在岗()（约156-209行）
  - 工具/活_本人.py：唤醒流程里 _工具间.上工(...) 打卡（约868-869行）
  - 工具/健康.py：中转站连接失败/429/AccessDenied 仅在故障话术层识别（约217、283行），不回写考勤
  - 考勤留痕：工具间/记录/YYYY-MM-DD.jsonl
- 修复建议（供开发组参考）：唤醒失败因限额/额度/连接失败时，在考勤板记"不可达"状态并带原因和时间戳；查在岗输出区分"在跑任务/空闲/不可达"三态；唤醒入口失败路径统一回写，不得只吞异常。
- 连带说明：本次值席替老钟代答属此bug的次生后果，不单列。

【BUG-002】责任席"纯承诺"收尾即结束回合，未开工的任务静默挂起；无输出回合被吞，全程靠船主催才推进

- 始末：2026-08-29 19:26 船主令建bug反馈文档 → 19:29 老梁回"这单我接了"后回合结束，未办 → 19:30 船主催"那做啊"，该回合无任何输出、无回复 → 19:44 船主"啊？" → 19:49 老梁致歉并再承诺"现在就干"，仍未办 → 19:50 船主斥"倒是动啊" → 19:56 才派阿强 → 19:57 文档落成。指令到完工29分钟，三次实质推进全由船主催促触发。
- 现象：责任席接到明确任务后，以"我接了/马上就办"这类纯意向回复结束回合，任务既不escalate也不派活、不留待办；船主侧只见沉默。"被唤醒但零输出"的回合被静默吞掉，船主无从知晓有人正在办还是没人办。每条新消息还先重试唤醒不可达的原经理（每次静默约20秒）才由代理接管，过程对船主不可见。
- 根因：
  1) 回合结束条件＝模型说完话，而非"事已启动"：纯承诺回复被当正常应答记入大厅并结束本轮（工具/大厅.py 活厅()，约265-287行）。
  2) 无"待办/未开工"台账：承诺后无记录、无超时催办、无看门狗重新唤醒。
  3) 零输出回合直接 return "", False，不给船主任何可见进展或告警（工具/大厅.py 约279-287行）。
  4) 代理租约接待成功即清租约（工具/大厅.py _唤醒聊天统筹()，约100行），下一句又走全套"先唤老钟失败→重建租约"（工具/大厅.py _唤醒统筹()，约42-71行），每轮隐性耗时约20秒且不留痕。
  5) 聊天责任席工具集无 assign_task，提示词也未强制"接活当轮必须escalate或明说缓办"（工具/平台_工具集.py 大厅承接工具名()，约493-497行；工具/活_本人.py _聊天系统提示()，约299-319行），模型可用"嘴上说办"代替真办。
- 关联代码/文件（相对公司根目录）：
  - 工具/大厅.py：活厅() 回合循环与静默返回分支（约265-287行）；_唤醒聊天统筹() 成功即清租约（约88-138行）；_唤醒统筹() 原经理优先重试（约42-71行）
  - 工具/活_本人.py：聊天唤醒() 回合随模型回复流结束而终止（约532-624行）；_聊天系统提示() 接活规矩（约299-319行）
  - 工具/平台_工具集.py：大厅承接工具名() 未含 assign_task（约493-497行）
  - 工具/经理代理.py：清租约()（约90-91行）
  - 证据留痕：工具间/记录/2026-08-29.jsonl（多次"上工约20秒即下工、零发言"打卡）、大厅/对话/2026-08-29.jsonl（18:50-19:59完整时间线）
- 修复建议（供开发组参考）：
  1) 责任席回合结束时若含办事意向而无实际工具动作（escalate/assign/handoff），强制当场决断或记入"待办台账"并超时自动催办，禁止静默收尾。
  2) 被唤醒但零输出的回合给船主可见进展提示；连续静默回合触发告警。
  3) 租约有效期内或原经理近期唤醒失败时跳过重试/加冷却，避免每条消息隐性损失约20秒；跳过动作留痕给船主可见。
  4) 聊天责任席工具集增加 assign_task，或提示词强制接活当轮escalate，禁止"纯承诺"收尾。

【BUG-003】系统对"事是否真启动"无任何问责信号：纯承诺即按完成收尾，不提醒、不催办、不记账（"奖励系统瘫痪"）

- 始末：2026-08-29，老梁复盘 19:26-19:59"全靠船主踹才推进"的过程（见 BUG-002）时，在思考过程里写下"奖励系统看起来完全瘫痪"；船主追问含义，老梁作答后，船主指示把该问题登记入本文档，并明确不需要写修复方案，由开发组研究。
- 现象：责任席以"接了/马上办"这类纯意向回复接活后，回合即按正常应答结束；系统没有任何机制发出"你还欠着一件没启动的活"这一信号——无提醒、无催办、无台账，本人下一轮被唤醒时也不知道自己欠着债。驱动干活的反馈整个缺失，每一步推进全靠船主人工催促。
- 根因：完成/回合结束信号挂在"模型说完话"上，而非"事已启动"；无待办台账、无超时催办、无看门狗重新唤醒。与 BUG-002 根因第1)、2)条同源，本条是其机制层面的表述，同根同源，开发组可自行判断合并或分列。
- 关联代码/文件：见 BUG-002"关联代码/文件"一节（回合结束条件、待办台账缺失），不另列。
- 修复建议：按船主指示不写，开发组自行研究。
